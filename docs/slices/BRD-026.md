# 🏗️ BRD-026 — Objectify the telemetry endpoint

## Status

Planned

## Goal

Complete the objectification of the NOC telemetry endpoint by moving application behaviour out of the procedural production entry point and into cohesive objects with explicit responsibilities.

This work was originally part of BRD-022 but was deliberately deferred so that dashboard notifications could be completed independently.

The endpoint's externally observable behaviour shall remain unchanged. This is an architectural refactoring, not a redesign of the telemetry protocol.

---

## Principles

- Preserve existing telemetry behaviour before improving it.
- Keep the production entry point free of application logic.
- Introduce classes only where they represent coherent responsibilities.
- Pass request data explicitly rather than allowing superglobals to leak through the object graph.
- Keep deployment configuration declarative unless objectification provides genuine behaviour or validation.
- Preserve PHP 5.5 compatibility throughout.
- Keep every refactoring step small enough for the complete test suite to remain green.

---

## Design

### Endpoint orchestration

Introduce a `TelemetryEndpoint` orchestration object responsible for coordinating one telemetry request.

Target shape:

```php
$endpoint = new TelemetryEndpoint(...);
$endpoint->handle($_SERVER, $_POST);
```

The production entry point may retain:

- configuration loading;
- required class-file loading;
- construction of the object graph;
- invocation of the endpoint.

It shall contain no application logic.

Endpoint-level characterisation coverage shall be established before the procedural entry point is replaced.

---

### Request handling

Move request validation out of the entry point.

The objectified path shall preserve:

- HTTP method validation;
- required-parameter validation;
- empty-string handling;
- existing error messages;
- existing HTTP status codes;
- existing response bodies;
- the plain-text content type;
- terminating newlines in response bodies.

Request data shall be passed explicitly after the entry-point boundary rather than reading `$_POST` throughout the object graph.

A dedicated request object may be introduced if it earns a clear responsibility, but is not required merely to wrap an array.

---

### Response handling

Replace the procedural `respond()` behaviour with an explicit endpoint responsibility.

Status, content type and response body emission shall be centralised.

Termination shall remain at the outermost HTTP boundary so response outcomes can be tested without terminating the test process.

---

### Authentication

Introduce an explicit authentication collaborator, such as `Authenticator`.

It shall:

- encapsulate host-token lookup;
- perform secure token comparison;
- preserve existing unknown-host behaviour;
- preserve existing invalid-token behaviour.

Deployment secrets shall remain outside version control.

Configuration data itself shall not become responsible for authentication behaviour.

---

### Schema loading and record construction

Introduce explicit responsibilities for loading heartbeat schemas and constructing telemetry records.

Likely collaborators include:

- `SchemaLoader`
- `RecordBuilder`

The objectified implementation shall preserve:

- host-specific schema lookup;
- missing and malformed schema behaviour;
- reserved-field protection;
- requested-field ordering and validation;
- schema-version handling;
- all supported value conversions;
- complete-record validation;
- existing exception types and messages.

Field selection may remain part of `RecordBuilder` unless it demonstrates a clear independent responsibility.

---

### Storage

Introduce an explicit telemetry storage boundary.

The storage responsibility shall:

- ensure the telemetry data directory exists;
- construct the appropriate daily JSONL filename;
- preserve host filename validation and path safety;
- append complete records appropriately for the current deployment model;
- preserve existing JSON encoding;
- preserve newline behaviour.

Archive rotation and consolidation remain separate concerns unless the existing design demonstrates that they naturally belong to this responsibility.

---

### Configuration boundaries

Review how configuration reaches `TelemetryEndpoint` and its collaborators.

Host tokens and the telemetry data directory shall remain outside the web root.

A configuration object shall be introduced only if it provides meaningful validation or behaviour.

Declarative PHP configuration, constants and arrays shall not be converted into objects merely for stylistic purity.

Deployment-time placeholder substitution and the rule that rendered configuration files are never committed shall be preserved.

---

### Procedural API retirement

Once production and test callers have migrated, review the standalone functions used by the telemetry path.

Behaviour should move to existing classes where it naturally belongs.

New classes should be introduced only for coherent responsibilities.

Genuinely generic stateless utility functions may remain where wrapping them in classes would provide no additional clarity.

Obsolete function files and `require_once` statements shall be removed when they are no longer needed.

The architectural requirement is:

> `telemetry.php` shall not call standalone application functions.

The goal is **not** to eliminate every standalone function from the codebase.

## Notes

This slice completes the architectural work deliberately deferred from BRD-022.

BRD-022 established `Noc` as the dashboard orchestration boundary and moved dashboard loading, presentation and rendering onto the new object-oriented path. This slice applies the same principle to the second production entry point without requiring the two paths to share abstractions that they do not genuinely have in common.

The intended result is symmetry at the application boundary:

```text
index.php
    ↓
   Noc

telemetry.php
    ↓
TelemetryEndpoint
```

Both production entry points become thin composition roots, while application behaviour lives behind explicit, testable responsibilities.

As with the dashboard objectification, the objective is not object orientation for its own sake. The objective is to make ownership and boundaries explicit while preserving the behaviour of a telemetry endpoint that already works.
