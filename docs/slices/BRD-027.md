# 🍕 BRD-027 — Normalise MikroTik version telemetry

## Status

Planned

## Goal

Clean up the MikroTik version telemetry so heartbeats contain only the underlying RouterOS version facts, while the client description derives update availability declaratively.

The MikroTik heartbeat currently reports:

```json
{
  "version": "7.23.1 (stable)",
  "latest_version": "7.23.3",
  "update_available": true
}
```

This mixes raw telemetry with derived state and represents the installed and latest versions inconsistently.

Replace these fields with:

```json
{
  "version": "7.23.1",
  "update_channel": "stable",
  "latest_version": "7.23.3"
}
```

The MikroTik client description shall then compare `version` with `latest_version` and generate the existing software-update notification when the latest version is newer.

---

## Principles

- Heartbeats contain facts.
- Client descriptions derive behaviour from those facts.
- Equivalent values should use equivalent representations.
- Derived state should not be transmitted when it can be expressed cleanly by an existing declarative rule.

---

## Design

### MikroTik heartbeat

Change the MikroTik heartbeat so the installed RouterOS version and update channel are reported separately.

Instead of:

```json
"version": "7.23.1 (stable)"
```

report:

```json
"version": "7.23.1",
"update_channel": "stable"
```

Continue reporting:

```json
"latest_version": "7.23.3"
```

Remove:

```json
"update_available": true
```

from the heartbeat.

The three remaining fields represent facts reported by RouterOS:

- `version` — currently installed RouterOS version;
- `update_channel` — configured RouterOS update channel;
- `latest_version` — latest version available on that channel.

---

## Client description

Update the MikroTik client description and schema to match the new heartbeat contract.

The client description shall derive update availability by comparing:

```text
latest_version > version
```

When a newer version is available, a declarative rule shall generate the software-update notification.

The notification shall include enough information to make both the available version and update channel unambiguous.

For example:

```text
RouterOS 7.23.3 is available on the stable channel.
```

No MikroTik-specific update comparison logic shall be introduced into dashboard PHP.

---

## Version comparison

Version comparison shall compare RouterOS version values semantically rather than as ordinary strings.

For example:

```text
7.23.3 > 7.23.1
```

shall evaluate as true.

The comparison mechanism should be generic enough to belong to the declarative rule system rather than being specific to MikroTik or RouterOS.

Only the comparison capability required by this slice should be introduced.

## Acceptance Criteria

- [ ] MikroTik `version` contains only the installed RouterOS version.
- [ ] MikroTik heartbeats include `update_channel`.
- [ ] MikroTik continues to report `latest_version`.
- [ ] MikroTik heartbeats no longer contain `update_available`.
- [ ] The MikroTik heartbeat schema reflects the new telemetry contract.
- [ ] The MikroTik client description reflects the new telemetry contract.
- [ ] The declarative rule system can determine whether `latest_version` is newer than `version`.
- [ ] Version comparison is generic and contains no MikroTik-specific logic.
- [ ] A newer available version produces the existing dashboard notification.
- [ ] The notification identifies both the available version and update channel.
- [ ] No notification is produced when the installed version is current.
- [ ] No client-specific update comparison logic is added to dashboard PHP.
- [ ] Existing unrelated MikroTik telemetry remains unchanged.
- [ ] The complete test suite remains green.

---

## Out of Scope

- Automatically installing RouterOS updates.
- Changing the configured RouterOS update channel.
- General dependency or package-update management.
- Client-specific version comparison logic.
- Changes to notification presentation.
- Changes to unrelated MikroTik telemetry.

---

## Notes

This slice removes `update_available` because it is derived information.

The heartbeat already contains the two facts needed to answer the question:

```text
version
latest_version
```

BRD-016 established the architectural principle that rules derive behaviour from heartbeat facts. Update availability therefore belongs naturally in the MikroTik client description rather than in the heartbeat producer.

Separating `update_channel` from `version` also gives each field a single meaning and allows the channel to be used independently in presentation.

The resulting flow becomes:

```text
MikroTik heartbeat
    │
    ├── version
    ├── update_channel
    └── latest_version
             │
             ▼
      declarative rule
             │
     latest > installed
             │
             ▼
        notification
```

This slice should remain deliberately small: normalise the telemetry, add the minimum generic comparison capability required to derive update availability, and update the existing notification rule.
