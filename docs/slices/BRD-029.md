# 🔐 BRD-029 — Reject non-scalar telemetry parameters

## Status

Planned

## Goal

Harden the telemetry endpoint against malformed POST request shapes by rejecting non-scalar parameter values before they reach code that casts, trims, or otherwise assumes scalar input.

The telemetry endpoint currently assumes ordinary scalar form parameters. Crafted requests such as:

```text
host[]=foo
```

may produce PHP array-to-string, `trim()`, or related type warnings before the request is ultimately rejected.

Production PHP errors are already hidden from HTTP clients, so this is not an information-disclosure issue. However, repeated malformed requests can generate unnecessary private log noise and rely on incidental PHP warning behaviour rather than an explicit request contract.

This slice makes request-shape validation deterministic.

---

## Design

### Scalar parameter contract

Telemetry request parameters that are expected to contain scalar values shall be validated as scalar before any:

- string casting;
- trimming;
- comparison;
- field selection;
- other scalar-specific processing.

Array-valued or otherwise unsupported request values shall be rejected cleanly.

---

### Validation boundary

Request-shape validation should happen as close as practical to the telemetry endpoint boundary.

Invalid request shapes must not be allowed to reach downstream collaborators such as `FieldSelector` in a form they do not support.

The implementation should reuse the existing endpoint/request-validation structure introduced by BRD-026 rather than introduce a new request framework.

---

### HTTP behaviour

Valid requests shall behave exactly as before.

Malformed non-scalar parameters shall produce a deterministic client error response using the existing telemetry endpoint error conventions as closely as practical.

The endpoint shall reject the request without producing PHP warnings or notices.

---

## Acceptance Criteria

- [ ] Required scalar telemetry parameters reject array-valued input cleanly.
- [ ] Optional scalar telemetry parameters reject array-valued input cleanly where applicable.
- [ ] Non-scalar values are rejected before casting, trimming, comparison, or field processing.
- [ ] Crafted input such as `host[]=foo` does not generate PHP warnings or notices.
- [ ] Malformed request shapes produce a deterministic HTTP error response.
- [ ] Existing valid-request behaviour is unchanged.
- [ ] Existing HTTP status and response-body conventions are preserved as much as practical.
- [ ] `FieldSelector` and other downstream collaborators do not receive unsupported array-valued parameters.
- [ ] Regression coverage includes representative array-valued POST parameters.
- [ ] The complete test suite remains green.

---

## Out of Scope

- Broader telemetry endpoint redesign.
- New request or response abstractions.
- Changes to authentication behaviour.
- Changes to schema validation.
- Changes to field-selection semantics for valid scalar input.
- Rate limiting or request throttling.
- Changes to PHP error-log configuration.
- Changes to the telemetry protocol beyond rejecting malformed request shapes.

---

## Notes

This slice is follow-up security hardening discovered during Christer’s review of BRD-026.

It is not a blocker for BRD-026 and does not indicate an information leak: production PHP errors are already suppressed from client responses.

The purpose is instead to make malformed input fail by explicit application logic rather than by incidental PHP warnings.

A hostile request should therefore result in:

```text
invalid request → controlled rejection
```

rather than:

```text
invalid request → PHP warning → controlled rejection
```

The distinction is small but important: malformed input should be part of the endpoint’s defined behaviour, not an accidental side effect of PHP’s type coercion.
