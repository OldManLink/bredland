# 🍕 BRD-019 — Standardise deployment status reporting

## Status

Planned

## Goal

Standardise deployment status reporting across all Bredland deployment scripts.

Deployment output should be easy to scan, clearly communicate progress, and make failures immediately visible. A failed deployment step must never be mistaken for a successful one.

This slice introduces a small shared helper library that provides consistent status reporting while keeping deployment-specific verification logic with the scripts that require it.

---

## Design

### Shared deployment helpers

Create:

```text
scripts/lib/deploy.sh
```

The helper library shall provide generic deployment helpers, including:

- `pass`
- `fail`
- `run_step`

These helpers shall be independent of any particular deployment target.

---

### Deployment scripts

Update the existing deployment scripts to use the shared helper library.

Deployment output shall use a consistent visual convention:

- `✅` for successful steps
- `❌` for failed steps

If any deployment step fails, the deployment shall terminate immediately.

---

### Target-specific verification

Verification that depends on the behaviour of a particular deployment target shall remain outside the shared helper library.

In particular, the MikroTik deployment shall continue to verify successful installation by inspecting explicit output markers, since RouterOS may report script errors without returning a failing SSH exit status.

---

## Acceptance Criteria

- ✅ `scripts/lib/deploy.sh` exists.
- ✅ Generic deployment helpers (`pass`, `fail`, `run_step`) are provided.
- ✅ Existing deployment scripts use the shared helpers for generic deployment steps where applicable.
- ✅ Successful deployments use a consistent `✅` status convention.
- ✅ Failed steps display a `❌` status and terminate the deployment.
- ✅ The shared helper library contains no RouterOS-specific logic.
- ✅ MikroTik deployment continues to verify script installation using explicit output markers.

---

## Notes

This slice standardises deployment behaviour without changing what is deployed.

The helper library should remain intentionally small and generic. Deployment targets with unusual verification requirements, such as RouterOS, should continue to implement those checks within their own deployment scripts.
