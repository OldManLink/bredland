# 🔐 BRD-036 — Asynchronous trusted action execution

## Status

Planned

## Goal

Allow trusted actions whose RouterOS execution takes significant time to run asynchronously on Bredland.

The trusted UI shall no longer need to keep its original action request open while MikroTik completes the operation.

Instead:

1. Bredland accepts a valid trusted action request;
2. assigns it a short-lived `request_id`;
3. starts the RouterOS operation in the background;
4. immediately returns acceptance to the browser;
5. remembers the eventual execution result temporarily;
6. allows the trusted UI to retrieve that result later.

This slice changes action execution mechanics only.

Telemetry remains authoritative for actual device state.

---

## Architectural Principle

There are three deliberately different facts:

```text
Bredland accepted the request
            ≠
MikroTik completed the command
            ≠
device reached the intended state
```

They shall not be collapsed into one success indication.

The trusted UI may report each relevant event, but only telemetry determines actual monitored device state.

---

## Intended Flow

```text
trusted UI
    │
    │ POST semantic action
    ▼
Bredland
    │
    ├── validate request
    ├── assign request_id
    ├── start RouterOS REST request asynchronously
    │
    └── return 202 + request_id
            │
            ▼
trusted UI
    │
    └── show "Request accepted"
            │
            │ later
            ▼
    fetch/poll request result
            │
            ▼
Bredland short-lived result
    │
    ├── pending
    ├── accepted
    └── failed
            │
            ▼
trusted UI
    └── show completion/failure toast
```

The exact naming of result states may be refined during implementation, but their semantics shall remain explicit.

---

## Action Submission

Existing trusted-action security boundaries remain unchanged.

The browser submits a semantic resolution.

It shall not submit:

- arbitrary RouterOS commands;
- RouterOS script names;
- REST paths;
- background process instructions;
- executable content.

Bredland shall continue to:

- recognise the semantic resolution;
- independently validate that the action is currently reasonable;
- map the resolution to its explicitly permitted RouterOS operation.

Only after those checks succeed may asynchronous execution begin.

---

## Accepted Response

Once Bredland has accepted the action for asynchronous execution, it shall return promptly with:

```text
HTTP 202 Accepted
```

and a generated:

```text
request_id
```

The response means only:

> Bredland accepted this request for execution.

It does not mean that MikroTik has completed the command.

It does not mean that the requested device-state change has occurred.

The trusted UI shall reflect this distinction.

---

## Request IDs

Each accepted asynchronous action shall receive an opaque `request_id`.

A request ID shall:

- identify one submitted execution;
- reveal no useful implementation detail;
- be suitable for later result retrieval;
- expire after a short, bounded lifetime.

Request IDs are correlation identifiers, not authority to initiate arbitrary actions.

Result retrieval shall remain restricted to the trusted Bredland path.

---

## Background Execution

After returning the accepted response, Bredland shall execute the already validated and mapped RouterOS operation independently of the original browser request.

The browser connection shall not need to remain open while MikroTik completes.

Completion of the RouterOS REST call shall update the corresponding short-lived request result.

Background execution shall preserve the least-privilege RouterOS boundary established by the existing trusted-action architecture.

Making execution asynchronous shall not broaden what Bredland is permitted to execute.

---

## Short-Lived Result State

Bredland shall retain a small, temporary result for each accepted `request_id`.

The minimum useful states are conceptually:

```text
pending
accepted
failed
```

where:

- `pending` means background execution has not yet completed;
- `accepted` means the RouterOS command completed successfully at the REST/action boundary;
- `failed` means background execution failed.

The exact names and response representation may be refined during implementation.

Results shall have a bounded lifetime and shall not become permanent NOC history.

No general-purpose job database is required.

---

## Result Retrieval

The trusted UI shall be able to retrieve the result associated with an accepted `request_id`.

For the first implementation, simple polling/fetching is sufficient.

No push mechanism is required.

Polling shall:

- remain bounded;
- avoid excessive request frequency;
- stop when a terminal result is received;
- stop after an appropriate timeout;
- handle an expired/unknown `request_id` cleanly.

This slice shall not introduce a general event or messaging system.

---

## UI Semantics

### First toast

After receiving:

```text
202 Accepted
```

the trusted UI shall show an acknowledgement such as:

```text
Request accepted
```

This toast means only that Bredland accepted the request for asynchronous execution.

It must not imply that MikroTik has completed the operation.

---

### Second toast

When later result retrieval reports successful background completion, the trusted UI shall show a second toast indicating that the MikroTik command completed.

Likewise, background execution failure may produce an advisory failure toast.

These messages describe execution of the command, not authoritative device state.

---

## Telemetry Remains Authoritative

Successful RouterOS command completion does not prove that the device has reached the intended operational state.

For example, a future update-staging command may complete successfully while the resulting package state still needs to be observed independently.

Therefore:

```text
action result
     ≠
device state
```

Existing and future heartbeat telemetry remains the canonical source of device state.

Rules and notifications shall continue to derive from telemetry rather than from asynchronous action-result records.

---

## Ephemeral Failure State

Background execution failures are advisory operational information for the trusted UI.

They shall not:

- become canonical NOC heartbeat state;
- modify stored telemetry;
- create synthetic heartbeat records;
- become persistent NOC notifications merely because an asynchronous command failed;
- be interpreted as authoritative device state.

The operator may retry an appropriate action after inspecting the failure and current telemetry.

---

## Harmless Feasibility Spike

Before converting a real trusted action to asynchronous execution, prove the complete mechanism using a harmless RouterOS script.

Provision a test script whose significant behaviour is:

```routeros
:delay 10s
```

with an obvious harmless completion result if useful for verification.

Invoke it through the same restricted RouterOS REST path used by real trusted actions.

The spike shall prove:

```text
browser
   ↓
Bredland accepts request
   ↓
202 + request_id returned promptly
   ↓
RouterOS REST continues in background
   ↓
10 second test script completes
   ↓
Bredland remembers result
   ↓
browser retrieves result
   ↓
completion UI appears
```

The browser must receive the initial acceptance substantially before the delayed RouterOS operation completes.

No package update or reboot is required to prove this architecture.

## TDD / Implementation Sequence

### 1. Characterise existing synchronous behaviour

Preserve tests describing the current trusted-action security and validation boundaries.

Identify the point at which the currently synchronous RouterOS call blocks the browser response.

---

### 2. Introduce request identity

Add deterministic tests proving that an accepted asynchronous action receives an opaque `request_id`.

Do not introduce background execution yet.

---

### 3. Introduce short-lived result storage

Add the smallest Bredland-owned mechanism capable of representing a request as pending and later terminal.

Test:

- creation;
- lookup;
- transition to success;
- transition to failure;
- unknown ID;
- expiry.

Avoid designing a generic job system.

---

### 4. Return acceptance immediately

Change action submission so a successfully validated asynchronous action returns:

```text
202 Accepted
```

with its `request_id`.

Test that this response represents acceptance only.

---

### 5. Execute harmless action in background

Provision and invoke the `:delay 10s` RouterOS test script.

Prove that the HTTP submission response returns before the RouterOS request completes.

Record the eventual result against the corresponding request ID.

---

### 6. Add result retrieval

Add the smallest trusted Bredland endpoint required to retrieve the short-lived result.

Test pending, successful, failed, unknown and expired results.

---

### 7. Add trusted UI polling

Extend Bredland-served `trusted.js` to retrieve the result after acceptance.

Keep polling bounded and stop on terminal state or timeout.

---

### 8. Separate the UI messages

Show the first toast when Bredland accepts the request.

Show the second toast only when later retrieval reports RouterOS command completion.

Verify that neither toast claims authoritative device state.

---

### 9. Prove background failure

Exercise a harmless failure path.

Verify that:

- initial acceptance may already have occurred;
- the later result becomes failed;
- the trusted UI reports that failure;
- telemetry and canonical NOC history remain untouched.

---

### 10. Review against future staging use case

Confirm that the resulting primitive is sufficient for a later slice to:

```text
request RouterOS package download
        ↓
receive immediate acceptance
        ↓
observe command completion
        ↓
wait for telemetry to report staged state
        ↓
offer separate install/reboot resolution
```

Do not implement that update-staging workflow in BRD-036.

## Security Invariants

- The public NOC remains observational.
- Trusted UI remains presentation, not authorization.
- A `request_id` does not grant authority to initiate arbitrary actions.
- Semantic resolutions remain inert until independently accepted and validated by Bredland.
- The browser never supplies arbitrary RouterOS commands or script names.
- Bredland retains ownership of resolution-to-operation mapping.
- Making execution asynchronous does not broaden RouterOS privilege.
- Result retrieval exposes only the bounded result associated with the trusted action.
- Ephemeral execution results never become canonical NOC state.

## Follow-on Use Case

The immediate expected consumer is a later RouterOS update-staging slice.

That workflow may eventually become:

```text
update available
      ↓
trusted "download" action
      ↓
Bredland accepts asynchronously
      ↓
RouterOS downloads package
      ↓
telemetry reports package staged
      ↓
new notification/resolution
      ↓
explicit install/reboot action
```

Crucially, BRD-036 does not infer `staged` from successful download-command completion.

The router must report that state through telemetry.

That preserves the established rule:

> Actions request change; telemetry reports reality.

## Notes

The approximately ten-second delay that motivated this slice exposed a useful ownership boundary.

The synchronous design currently makes browser request lifetime depend on RouterOS operation duration:

```text
browser ───────── waits ─────────► MikroTik
```

BRD-036 moves that responsibility to the component already responsible for trusted execution:

```text
browser ── request ──► Bredland
        ◄── 202 ──────

                       Bredland ──► MikroTik
                                  ...slow work...
                       Bredland ◄── completion

browser ── result? ──► Bredland
        ◄── result ───
```

The important part is not merely making the UI faster.

It makes the semantics more truthful.

A green response after ten seconds currently risks visually conflating several events. BRD-036 gives each one its proper meaning:

```text
accepted by Bredland
completed by MikroTik
observed through telemetry
```

That separation will become particularly valuable once trusted actions initiate operations whose device effects naturally outlive the initiating HTTP request.
