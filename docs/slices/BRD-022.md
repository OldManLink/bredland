# ✨ BRD-022 — Display dashboard notifications

## Completed

Planned

## Goal

Display active notifications produced by the declarative rules engine directly on the client cards that generated them.

Notifications shall provide a clear but unobtrusive indication that a monitored client requires attention, using a familiar count-badge interaction inspired by mobile application notification badges.

The first real notification shall report an available MikroTik RouterOS update using the telemetry introduced by BRD-015 and BRD-021.

---

## Design

### Notification source

Notifications are derived by the generic rules mechanism introduced in BRD-016.

For the MikroTik client, its description shall declare a rule equivalent to:

```json
{
  "when": {
    "field": "update_available",
    "equals": true
  },
  "then": [
    {
      "type": "notification",
      "text": "RouterOS {{latest_version}} is available."
    }
  ]
}
```

No MikroTik-specific notification logic shall exist in dashboard PHP.

---

### Notification badge

Each client card with one or more active notifications shall display a red circular count badge.

The badge shall:

- be visually associated with the client card that generated the notifications;
- use a familiar application-notification style;
- display the number of active notifications for that client;
- be absent when the client has no active notifications.

The badge should slightly overlap the card boundary rather than consume space within the card's normal content.

---

### Notification popover

Tapping the notification badge shall open a lightweight popover associated with that client card.

The popover shall display all currently active notifications for that client.

It shall include an explicit `×` control for closing the popover.

The popover shall close when:

- the `×` control is tapped;
- the notification badge is tapped again;
- another client's notification badge is tapped;
- the user taps anywhere outside the popover;
- the page is reloaded or refreshed.

Only one notification popover shall be open at a time.

---

### Interaction inside the popover

Interaction inside the popover shall **not** close it.

In particular, notification text shall remain selectable so that it can be copied.

Closing the popover affects only transient UI state. It does not acknowledge, dismiss, or modify the underlying notification.

---

### Stateless notifications

Notifications shall be derived entirely from the latest heartbeat and client description.

No notification state shall be persisted.

When a rule condition ceases to be true, its notification automatically disappears.

There is therefore no acknowledgement or notification-dismissal mechanism in this slice.

---

## First use case

The MikroTik client shall display a notification when:

```text
update_available == true
```

using the message:

```text
RouterOS {{latest_version}} is available.
```

For example:

```text
RouterOS 7.23.2 is available.
```

When subsequent telemetry reports:

```json
"update_available": false
```

the notification and its badge shall disappear automatically.

## Acceptance Criteria

- ✅ Notifications produced by BRD-016 rules are exposed on the dashboard.
- ✅ A client with active notifications displays a red count badge on its card.
- ✅ The badge displays the number of active notifications for that client.
- ✅ Clients without active notifications display no badge.
- ✅ Tapping the badge opens a popover containing all active notifications for that client.
- ✅ Only one notification popover may be open at a time.
- ✅ The popover can be closed using its `×` control.
- ✅ Tapping the badge again closes its open popover.
- ✅ Tapping outside the popover closes it.
- ✅ Tapping another notification badge closes the current popover and opens the selected one.
- ✅ Interaction inside the popover does not close it.
- ✅ Notification text can be selected and copied.
- ✅ Reloading or refreshing the page closes the popover.
- ✅ Notification messages may interpolate heartbeat fields.
- ✅ The MikroTik client displays the available RouterOS version as a notification.
- ✅ The MikroTik notification disappears automatically when `update_available` becomes false.
- ✅ No notification state is persisted.
- ✅ No client-specific notification logic is added to dashboard PHP.

---

## Out of Scope

- Notification history.
- Acknowledging or dismissing notifications.
- Global notification counters.
- Push notifications.
- Email or other external alerts.
- Notification severity or prioritisation.
- Client health or LED changes.
- Sounds.

---

## Notes

The badge and popover are presentation mechanisms for live rule results, not a messaging system.

A notification exists precisely while its declarative rule evaluates to true:

```text
condition true  → notification exists
condition false → notification does not exist
```

Closing the popover never changes that state.

This slice is the first user-facing consumer that brings together the boolean telemetry introduced by BRD-015, the declarative rules introduced by BRD-016, and the MikroTik `latest_version` telemetry introduced by BRD-021.
