# 🍕 BRD-018 — One Shot Miner telemetry client

## Status

Planned

## Goal

Add the One Shot Miner (OSM) as a first-class monitored NOC client.

Bredland shall collect telemetry from the OSM over the trusted local network, normalize the selected values into the existing heartbeat model, and send an ordinary heartbeat to the NOC.

The architecture shall remain:

```text
One Shot Miner
      ↓
 local REST API
      ↓
   Bredland
      ↓
normal NOC heartbeat
      ↓
     NOC
```

The public NOC shall have no knowledge of the OSM-specific API.

---

## Architectural Principle

The OSM is a local device with its own telemetry representation.

That representation belongs at the infrastructure boundary.

Bredland shall translate the OSM API into the generic heartbeat contract already understood by the NOC.

Therefore:

> OSM-specific collection lives on Bredland; normalized monitoring facts cross the NOC boundary.

The dashboard shall discover and render the OSM through the same self-describing client mechanism as existing clients.

No OSM-specific dashboard PHP shall be introduced.

---

## Source API

The current OSM runs NMMiner firmware.

Its local telemetry API shall be treated as an external device interface owned by the miner firmware rather than as part of the NOC contract.

Before fixing the production field mapping, inspect the live API response and confirm the semantics and types of every value selected for monitoring.

Do not copy display-oriented strings into heartbeat telemetry when a canonical numeric value is available.

---

## Collection

Bredland shall periodically retrieve telemetry from the OSM over the trusted LAN.

Collection shall:

- use the OSM's local API;
- have a bounded network timeout;
- fail cleanly when the miner is unavailable;
- avoid blocking unrelated Bredland functionality;
- normalize selected values before forwarding them;
- send telemetry through the existing NOC heartbeat endpoint and schema machinery.

Bredland remains a collector, not a second history store.

Historical OSM telemetry belongs to the NOC like every other heartbeat history.

---

## Heartbeat Identity

The OSM shall have its own NOC host identity and authentication token.

Its heartbeat shall be independent of Bredland's own heartbeat.

Conceptually:

```text
host: bredland
    → facts about Bredland

host: osm
    → facts about the One Shot Miner
```

Bredland merely transports the OSM heartbeat.

It shall not merge OSM telemetry into the Bredland heartbeat.

---

## Initial Telemetry

The initial heartbeat should remain deliberately small.

Candidate fields include:

```text
hash_rate
uptime
version
rssi
free_heap
best_difficulty
valid_blocks
ttl
```

The final initial set shall be confirmed against the live OSM API during implementation.

### `hash_rate`

Report the miner's current hash rate as a numeric value using a canonical unit.

Prefer the raw numeric API value over a formatted display string.

### `uptime`

Report the miner's current device/mining-session uptime.

Confirm the precise API semantics before binding the field.

Do not substitute Bredland collector uptime.

### `version`

Report the OSM/NMMiner firmware version.

### `rssi`

Report the miner's Wi-Fi signal strength using the numeric value supplied by the device.

### `free_heap`

Report available heap memory when supplied reliably by the firmware.

### `best_difficulty`

Report the miner's best-difficulty value only after confirming whether the selected source represents session best, lifetime best, or another clearly defined quantity.

The heartbeat field name or description shall reflect the actual semantics.

### `valid_blocks`

Include a valid-block/block-hit count only after confirming the precise meaning of the underlying OSM field.

Do not promote an ambiguously named API value merely because it appears useful.

### `ttl`

Report the normal heartbeat TTL according to the established producer-owned cadence contract.

---

## API Investigation

Before finalising the mapping, capture a representative response from the live miner and classify candidate source fields.

For each selected value determine:

- source field/path;
- meaning;
- raw type;
- canonical heartbeat type;
- unit;
- whether it is session-scoped or lifetime-scoped;
- whether zero is a legitimate value;
- whether absence/unavailability needs special handling.

Pay particular attention to values whose firmware names may be ambiguous, including difficulty/share/block counters.

This investigation is part of BRD-018 because the adapter contract cannot be considered complete until the source semantics are understood.

It shall not grow into general reverse engineering of the NMMiner API.

---

## Normalization

The collector shall convert OSM values into canonical heartbeat types before submission.

Use the existing heartbeat types:

```text
integer
float
string
boolean
```

as appropriate.

Display formatting does not belong in the collector.

For example:

```text
1000000
```

is preferable heartbeat data to:

```text
"1.00 MH/s"
```

when the underlying value represents a numeric hash rate.

The client description remains responsible for presentation metadata and formatting.

---

## Failure Behaviour

Failure to collect OSM telemetry shall not cause Bredland to fabricate a healthy heartbeat.

If the miner cannot be reached or its response cannot be safely interpreted, the OSM heartbeat shall not falsely claim current telemetry.

The existing NOC heartbeat TTL/health mechanisms shall then naturally expose stale or missing OSM state.

Collector failure shall not interfere with Bredland's own heartbeat or unrelated Bredland services.

---

## Client Description

Add a self-describing NOC client definition for the OSM.

It shall describe:

- display name;
- ordering;
- selected heartbeat fields;
- value types;
- formatters/presentation metadata as required;
- TTL/health behaviour using the existing architecture.

The dashboard shall require no OSM-specific code.

Once the heartbeat and client description exist, the normal NOC pipeline shall be sufficient to render the miner.

---

## Rules and Notifications

Only add OSM Rules where a concrete operational condition is understood well enough to justify one.

BRD-018 does not require inventing warning thresholds merely to demonstrate the Rule machinery.

Basic successful monitoring is sufficient for the first slice.

Any useful thresholds discovered during implementation may be included if they are obvious, deterministic and genuinely useful; otherwise they belong in later slices.

---

## TDD / Implementation Sequence

### 1. Capture and understand the live API

Retrieve a representative response from the real OSM.

Document the source fields relevant to the initial heartbeat and verify their semantics.

Resolve ambiguous candidates before relying on them.

---

### 2. Characterise the collector boundary

Create deterministic OSM API fixtures from representative device responses.

Add tests proving that the collector can consume the relevant response without requiring the real miner.

---

### 3. Normalize one field

Start with the simplest unambiguous telemetry value.

For example:

```text
version
```

or:

```text
hash_rate
```

Drive the translation from OSM representation to canonical heartbeat value with a failing test.

Implement only enough adapter behaviour to make it pass.

---

### 4. Add the remaining selected fields

Introduce the agreed initial telemetry one field at a time.

For each field test:

- source extraction;
- type conversion;
- unit/semantic normalization;
- unavailable/malformed behaviour where relevant.

Keep the adapter explicit and boring.

---

### 5. Add collection failure behaviour

Test at least:

- OSM unreachable;
- timeout;
- malformed response;
- missing required data.

Verify that failure does not fabricate a successful current heartbeat or interfere with unrelated Bredland behaviour.

---

### 6. Submit a canonical heartbeat

Drive the integration between the normalized OSM telemetry and the existing NOC telemetry endpoint.

Use the OSM's own host/token identity.

Verify that Bredland's own heartbeat remains completely independent.

---

### 7. Add the OSM client description

Create the self-describing OSM client definition.

Verify it using the existing client-description/compiler tests.

No dashboard-specific implementation shall be necessary.

---

### 8. Render through the ordinary NOC

Use deterministic heartbeat fixtures to prove that the existing dashboard renders the OSM card and selected fields correctly.

Any required formatting shall use existing generic formatter mechanisms.

---

### 9. Exercise the real path

Run the collector against the real OSM:

```text
OSM
 ↓
Bredland
 ↓
NOC endpoint
 ↓
stored heartbeat
 ↓
dashboard
```

Compare the resulting heartbeat with the miner's live telemetry.

---

### 10. Verify history

After enough heartbeats have accumulated, use the existing NOC history endpoint to verify that OSM history is stored and retrieved exactly like history for existing clients.

No OSM-specific history implementation shall be introduced.

---

## Out of Scope

- Controlling the OSM.
- Restarting the miner.
- Changing mining pools.
- Changing wallet configuration.
- Changing Wi-Fi configuration.
- Generic local-device control.
- OSM history storage on Bredland.
- OSM-specific NOC history APIs.
- OSM-specific dashboard PHP.
- Reverse engineering the entire NMMiner API.
- Automatically inventing alert thresholds.
- Mining profitability calculations.
- Bitcoin price telemetry unless separately justified.
- Pool-side telemetry.
- Changes to the existing heartbeat-history architecture.

---

## Notes

BRD-018 was originally conceived before much of the current NOC architecture existed.

That architecture now gives the implementation a deliberately short path:

```text
OSM-specific world
       │
       ▼
 Bredland adapter
       │
       ▼
generic heartbeat
       │
       ▼
existing NOC machinery
```

The interesting work therefore belongs almost entirely at one boundary:

> Translate what the miner says into facts the NOC already knows how to handle.

Once that translation is correct, the rest should be intentionally uneventful.

The OSM should gain storage, TTL behaviour, rendering, history and future Rule support primarily by **not being special**.

That is the architectural payoff this long-delayed slice gets to collect. 😄
