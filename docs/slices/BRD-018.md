# 🍕 BRD-018 — One Shot Miner telemetry client

## Status

Completed

## Goal

Add the One Shot Miner (OSM) as a first-class monitored NOC client.

Bredland shall collect telemetry from the OSM over the trusted local network, normalize the selected values into the existing heartbeat model, and send an ordinary heartbeat to the NOC.

The architecture shall remain:

```text
One Shot Miner
      ↓
 local REST API
      ↓
   Bredland
      ↓
normal NOC heartbeat
      ↓
     NOC
```

The public NOC shall have no knowledge of the OSM-specific API.

---

## Architectural Principle

The OSM is a local device with its own telemetry representation.

That representation belongs at the infrastructure boundary.

Bredland shall translate the OSM API into the generic heartbeat contract already understood by the NOC.

Therefore:

> OSM-specific collection lives on Bredland; normalized monitoring facts cross the NOC boundary.

The dashboard shall discover and render the OSM through the same self-describing client mechanism as existing clients.

No OSM-specific dashboard PHP shall be introduced.

---

## Source API

The current OSM runs NMMiner firmware v2.0.03.

Its local telemetry API is treated as an external device interface owned by the miner firmware rather than as part of the NOC contract.

The implementation uses two OSM endpoints:

```text
/api/system/info
/probe
```

Representative responses were captured as deterministic fixtures before the production mapping was fixed.

Display-oriented strings are not copied into heartbeat telemetry when a canonical numeric value is available.

---

## Collection

Bredland periodically retrieves telemetry from the OSM over the trusted LAN.

Collection:

- uses the OSM's local API;
- uses a bounded five-second network timeout for each OSM request;
- fails cleanly when the miner is unavailable;
- fails cleanly when collection times out;
- fails cleanly when the response cannot be parsed;
- rejects missing required telemetry;
- avoids blocking unrelated Bredland functionality;
- normalizes selected values before forwarding them;
- sends telemetry through the existing NOC heartbeat endpoint and schema machinery.

The production collector runs independently from Bredland's own heartbeat.

Bredland remains a collector, not a second history store.

Historical OSM telemetry belongs to the NOC like every other heartbeat history.

---

## Heartbeat Identity

The OSM has its own NOC host identity and authentication token.

Its heartbeat is independent of Bredland's own heartbeat.

Conceptually:

```text
host: bredland
    → facts about Bredland

host: osm
    → facts about the One Shot Miner
```

Bredland merely transports the OSM heartbeat.

It does not merge OSM telemetry into the Bredland heartbeat.

## Initial Telemetry

The completed initial heartbeat deliberately remains small:

```text
hash_rate
uptime
version
rssi
free_heap
best_difficulty_ever
block_hits
ttl
```

### `hash_rate`

Source:

```text
/probe.hr
```

Canonical heartbeat representation:

```text
integer
```

Unit:

```text
H/s
```

Example:

```text
1040183
```

Display formatting remains a dashboard concern and currently renders this as:

```text
1040.2 kH/s
```

### `uptime`

Source:

```text
/probe.ut
```

Canonical heartbeat representation:

```text
integer
```

Unit:

```text
seconds
```

The selected value represents OSM uptime since boot.

It is not Bredland collector uptime.

### `version`

Source:

```text
/api/system/info.identity.fwVersion
```

Canonical heartbeat representation:

```text
string
```

Example:

```text
v2.0.03
```

### `rssi`

Source:

```text
/api/system/info.identity.rssi
```

Canonical heartbeat representation:

```text
integer
```

Unit:

```text
dBm
```

### `free_heap`

Source:

```text
/api/system/info.miner.freeHeap
```

Canonical heartbeat representation:

```text
integer
```

Unit:

```text
bytes
```

### `best_difficulty_ever`

Source:

```text
/probe.ebd
```

Canonical heartbeat representation:

```text
integer
```

This is the miner's lifetime/high-water-mark best difficulty.

The canonical numeric `/probe` value is deliberately preferred over the display-oriented string supplied elsewhere by the firmware, for example:

```text
"5.3061K"
```

becoming:

```text
5306
```

The session-scoped `/probe.sbd` value is intentionally not exposed under this field.

### `block_hits`

Source:

```text
/api/system/info.miner.blkhits
```

Canonical heartbeat representation:

```text
integer
```

The field is named `block_hits` rather than the earlier provisional `valid_blocks` so that the heartbeat does not claim stronger semantics than the firmware field supports.

Zero is a legitimate value.

### `ttl`

Collector-owned canonical heartbeat value:

```text
600
```

Unit:

```text
seconds
```

The OSM heartbeat runs every ten minutes and uses the established producer-owned TTL contract.

## API Investigation

Representative live OSM API responses were inspected before finalising the mapping.

For each selected value the implementation established:

- source field/path;
- meaning;
- raw type;
- canonical heartbeat type;
- unit where applicable;
- session/lifetime semantics where relevant;
- whether zero is legitimate;
- required-field behaviour.

Particular attention was paid to the firmware's difficulty and block-related values.

The resulting contract deliberately avoids ambiguous names.

Notably:

```text
/probe.sbd
    → session best difficulty
    → not exposed

/probe.ebd
    → lifetime/ever best difficulty
    → best_difficulty_ever

miner.blkhits
    → block-hit counter
    → block_hits
```

This investigation remained bounded to the telemetry required by BRD-018 rather than becoming general reverse engineering of the NMMiner API.

---

## Normalization

The collector converts OSM values into canonical heartbeat types before submission.

The existing heartbeat types remain:

```text
integer
float
string
boolean
```

as appropriate.

Display formatting does not belong in the collector.

For example:

```text
1040183
```

is heartbeat data.

```text
1040.2 kH/s
```

is presentation.

The client description remains responsible for presentation metadata and formatting.

---

## Failure Behaviour

Failure to collect OSM telemetry does not cause Bredland to fabricate a healthy heartbeat.

The collection path explicitly verifies:

```text
OSM unreachable
    → collection fails
    → no telemetry POST

OSM request timeout
    → collection fails
    → no telemetry POST

malformed OSM response
    → collector fails
    → heartbeat script stops
    → no telemetry POST

missing required field
    → collector rejects input
```

Collector-process failure is propagated directly by the heartbeat script rather than being hidden inside shell process substitution.

The existing NOC heartbeat TTL/health mechanism therefore exposes stale or missing OSM state naturally.

OSM collection runs as its own service/timer and does not interfere with Bredland's own heartbeat.

---

## Client Description

The OSM has a self-describing NOC client definition.

It describes:

- display name;
- ordering;
- selected heartbeat fields;
- value types;
- formatters/presentation metadata;
- normal TTL/health behaviour through the existing architecture.

The OSM card currently displays:

```text
Uptime
Hash rate
```

with the remaining selected fields available through the normal telemetry drawer.

The dashboard contains no OSM-specific PHP.

Once the heartbeat and client description exist, the normal NOC pipeline renders the miner as an ordinary client.

## Implementation Verification

The production collector was deployed to Bredland as an independent systemd oneshot service driven by its own timer.

The first real OSM heartbeat successfully travelled through the complete generic path:

```text
OSM
 ↓
Bredland collector
 ↓
ordinary telemetry endpoint
 ↓
canonical heartbeat store
 ↓
generic NOC renderer
```

A representative production heartbeat was:

```json
{
  "schema": 1,
  "host": "osm",
  "ttl": 600,
  "uptime": 752801,
  "hash_rate": 1025904,
  "version": "v2.0.03",
  "rssi": -72,
  "free_heap": 54216,
  "best_difficulty_ever": 5306,
  "block_hits": 0
}
```

Subsequent heartbeats accumulated at approximately ten-minute intervals.

History retrieval showed the OSM records through the existing generic endpoint with no special-case implementation.

The production heartbeat was also compared against fresh live values from both OSM source endpoints.

Stable values matched directly:

```text
version
best_difficulty_ever
block_hits
```

while naturally dynamic values showed plausible elapsed-time/live variation:

```text
uptime
hash_rate
rssi
free_heap
```

The comparison also confirmed the deliberate use of:

```text
/probe.ebd = 5306
```

rather than the firmware's display-oriented:

```text
"5.3061K"
```

Failure behaviour was subsequently hardened and tested so that:

```text
unreachable
timeout
malformed response
missing required data
```

all prevent a fresh telemetry POST.

The complete automated test suite and local NOC preview were green after the final failure-path changes.

## Notes

BRD-018 was originally conceived before much of the current NOC architecture existed.

That architecture gave the implementation a deliberately short path:

```text
OSM-specific world
       │
       ▼
 Bredland adapter
       │
       ▼
generic heartbeat
       │
       ▼
existing NOC machinery
```

The interesting work belonged almost entirely at one boundary:

> Translate what the miner says into facts the NOC already knows how to handle.

Once that translation was correct, storage, TTL behaviour, rendering and history all arrived primarily by **not making the OSM special**.

That is the architectural payoff this long-delayed slice finally collected. 😄
