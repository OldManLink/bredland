# 🍕 BRD-024 — Add heartbeat TTL telemetry

## Status

Planned

## Goal

Have every existing telemetry client declare how long its latest heartbeat should be considered current.

Both existing clients shall include a `ttl` field in their heartbeats so consumers can determine whether a heartbeat is overdue from the heartbeat itself, rather than relying on a hard-coded expected interval.

This slice changes client telemetry only. It does not change NOC behaviour.

---

## Motivation

The NOC currently needs to know when the next heartbeat is expected, but that knowledge is derived from a hard-coded client cadence.

That creates an unnecessary external assumption about client behaviour.

The client already knows how frequently it intends to report, so that expectation should travel with the heartbeat as data.

A consumer can then determine expiry conceptually as:

```text
heartbeat timestamp + ttl
```

If the current time is later than that point, the expected next heartbeat is delayed.

---

## Design

### Heartbeat field

Both existing clients shall include:

```json
"ttl": 300
```

where `ttl` is an integer number of seconds.

The actual value is client-specific and shall reflect that client's intended heartbeat interval.

`ttl` describes the validity period of the heartbeat. It is not a timestamp and does not represent elapsed time.

---

### Client ownership

Each telemetry client is responsible for supplying its own `ttl`.

This keeps knowledge of heartbeat cadence with the producer rather than duplicating it in consumers.

Changing a client's reporting cadence shall therefore require changing the client configuration or heartbeat generation, not NOC code.

---

### NOC

No NOC behaviour changes are part of this slice.

The NOC may receive and store the new field through the existing generic telemetry path, but consuming `ttl` to determine heartbeat freshness belongs to the follow-up work that motivated this slice.

---

## Acceptance Criteria

- [ ] Both existing telemetry clients include a `ttl` field in every heartbeat.
- [ ] `ttl` is represented as an integer number of seconds.
- [ ] Each client's `ttl` reflects its intended heartbeat interval.
- [ ] The corresponding heartbeat schemas include `ttl`.
- [ ] Existing telemetry continues to be sent unchanged apart from the additional field.
- [ ] No NOC application code changes are required.
- [ ] Existing tests continue to pass, with fixtures updated where necessary.

---

## Out of Scope

- Changing heartbeat cadence.
- Changing NOC freshness or health calculations.
- Changing dashboard rendering.
- Adding tolerance or grace periods around late heartbeats.
- Using `ttl` in deployment safety calculations.
- Changes to BRD-022 beyond enabling its cleaner completion.

---

## Notes

This slice moves knowledge to the place that owns it:

> The client knows when it intends to report again.

Consumers should not need to know whether a particular client reports every minute, every five minutes, or on some other cadence.

BRD-022 revealed the need for this field, but the telemetry contract is sufficiently independent to warrant its own small slice and branch.
