# 🔐 BRD-030 — Trusted-network dashboard mode

## Status

Planned

## Goal

Allow the NOC dashboard to discover when it is being viewed from the trusted home-management network and, only in that context, load a separate trusted-mode presentation from Bredland.

The ordinary public NOC shall remain observational and unchanged in capability.

Trusted mode in this slice is a **presentation state only**. It does not grant authority to perform privileged actions.

No privileged actions are implemented by this slice. Authorization and execution of trusted actions belong to BRD-031.

---

## Architectural Principle

> The public NOC may know how to discover whether Bredland is reachable, but it must not contain knowledge of what trusted mode looks like or does.

The public dashboard therefore contains only the minimum bootstrap behaviour required to:

1. silently probe Bredland;
2. determine whether trusted mode is available;
3. after a successful probe, load trusted-mode assets from Bredland.

Everything that defines trusted mode belongs on Bredland.

---

## Trust Model

Trusted mode may become available when the browser can reach Bredland through the trusted home-management network, including:

- the home LAN;
- WireGuard access to the home network.

Successful discovery means only:

> This browser can reach the trusted-mode resources exposed by Bredland.

It does **not** mean:

> This browser is authorized to perform privileged actions.

The distinction is fundamental.

A user who manually manipulates the public dashboard in browser developer tools must at most be able to imitate trusted-mode presentation.

Doing so must confer no additional authority.

BRD-031 shall establish an independent authorization and execution boundary for privileged actions.

---

## Design

### Public dashboard bootstrap

On load, the ordinary public dashboard shall silently attempt to reach a small trusted-mode discovery endpoint served by Bredland.

The bootstrap code required to perform this probe may be shipped as part of the public NOC.

It shall contain no knowledge of trusted-mode behaviour beyond what is strictly necessary to perform discovery and request the trusted assets after successful discovery.

---

### Normal public behaviour

Failure to reach Bredland is the expected normal case for public dashboard access.

If the probe fails:

- the dashboard continues operating normally;
- trusted mode is not enabled;
- no trusted-mode assets are requested;
- no application-visible warning or error is displayed;
- no degraded state is displayed;
- no repeated retry loop is started;
- ordinary dashboard behaviour remains unchanged.

The failed probe must be operationally uninteresting to the user.

---

### Successful discovery

If the Bredland probe succeeds, the public bootstrap may load the trusted-mode assets.

Trusted mode shall not be implemented by public NOC assets.

Instead, the browser shall load the trusted-mode implementation directly from Bredland.

---

## Trusted Asset Separation

### JavaScript

All JavaScript specific to trusted mode shall be served by Bredland.

The ordinary public NOC shall not ship trusted-mode JavaScript.

This includes implementation details such as:

- trusted-mode behaviour;
- future privileged-control plumbing;
- action names;
- trusted-only strings;
- comments describing trusted capabilities;
- dormant trusted-mode code paths.

The public dashboard contains only the minimal bootstrap required for discovery and subsequent trusted-asset loading.

---

### CSS

The same separation applies to trusted-mode styling.

All CSS specific to trusted mode shall be served by Bredland and loaded only after successful trusted-mode discovery.

Ordinary public NOC stylesheets shall not contain:

- trusted-mode selectors;
- trusted-mode classes;
- trusted-mode visual rules;
- comments describing trusted presentation;
- dormant trusted-mode styling.

The public NOC therefore does not know how trusted mode looks.

---

### Resource naming

Trusted-mode assets should use opaque or fingerprinted resource names.

For example, resource URLs should not casually advertise concepts such as:

```text
admin.js
trusted-mode.js
router-actions.js
```

The purpose is disclosure minimisation: casual inspection of browser developer tools should reveal as little as practical about the purpose of resources loaded from Bredland.

Opaque naming is **not** an authorization mechanism.

Knowledge or discovery of a trusted resource URL must never confer authority to perform privileged operations.

---

### Production metadata

Production trusted assets shall not publish source maps or similarly revealing development metadata.

The production delivery mechanism should avoid unnecessary disclosure of:

- original source filenames;
- internal module structure;
- comments;
- development paths;
- other implementation metadata not required by the browser.

This is disclosure minimisation, not a substitute for the authorization boundary required by BRD-031.

---

## Trusted-Mode Presentation

The initial trusted-mode presentation shall be deliberately subtle.

When trusted mode is active, a thin border shall appear around the dashboard viewport in a slightly different shade of grey from the ordinary dashboard.

The cue should be:

- noticeable to the operator who knows what to look for;
- sufficient to distinguish trusted mode from ordinary public mode;
- unobtrusive;
- visually consistent with the existing dashboard;
- unlikely to draw attention from a casual observer.

The styling that creates this border shall exist only in CSS loaded from Bredland after successful trusted-mode discovery.

No equivalent trusted-mode selector or styling shall be present in the ordinary public NOC assets.

---

## Feasibility Spike

Before building the complete trusted-mode implementation, prove that the fundamental browser interaction works cleanly.

From:

```text
https://noc.arcanel.se/
```

the browsers used for the NOC shall be able to:

1. silently attempt to reach Bredland;
2. distinguish successful reachability from ordinary failure;
3. after success, load JavaScript from Bredland;
4. after success, load CSS from Bredland;
5. continue normally when Bredland cannot be reached.

The spike shall specifically exercise relevant browser constraints, including:

- HTTPS;
- CORS;
- CSP;
- browser local-network access restrictions.

If this primitive cannot be made to work cleanly in the browsers we care about, stop and revise the discovery/delivery mechanism before implementing the remainder of the slice.

The feasibility spike exists to validate the architectural assumption, not to force the chosen mechanism through incompatible browser security boundaries.

---

## TDD / Implementation Sequence

### 1. Characterise ordinary public behaviour

Establish tests covering the existing public dashboard before introducing trusted discovery.

Verify that ordinary rendering and behaviour remain unchanged.

### 2. Prove browser feasibility

Implement the smallest possible Bredland probe and asset-loading spike.

Verify it manually in the supported browser environments before building additional trusted-mode infrastructure.

If the primitive proves unsuitable, revise the design before continuing.

### 3. Introduce silent discovery

Add the minimal public bootstrap necessary to probe Bredland.

Drive behaviour with tests covering:

- successful discovery;
- failed discovery;
- absence of visible errors;
- absence of retries;
- preservation of normal public behaviour.

### 4. Introduce trusted JavaScript delivery

After successful discovery, load a minimal trusted JavaScript asset from Bredland.

Verify that it is not present in or requested by the ordinary public path.

### 5. Introduce trusted CSS delivery

Load trusted-mode CSS from Bredland only after successful discovery.

Use it to introduce the trusted-mode viewport border.

Verify that no trusted-mode styling exists in public NOC assets.

### 6. Harden asset disclosure

Introduce opaque/fingerprinted production resource naming and ensure production trusted assets expose no source maps or similarly unnecessary metadata.

### 7. Verify the security boundary

Demonstrate that locally spoofing trusted-mode presentation does not provide any privileged capability.

At the end of BRD-030 there should, in fact, be no privileged capability to obtain.

## Out of Scope

- Performing privileged actions.
- Updating RouterOS.
- Buttons or other action controls.
- Authorization of privileged operations.
- Capability tokens.
- Short-lived or single-use action credentials.
- Command queues.
- Bredland-mediated command execution.
- Oderland-mediated command storage or forwarding.
- General remote-control infrastructure.
- Treating successful discovery as proof of authorization.
- Persistent trusted-mode state.
- Trusted-mode notification actions.

All privileged-action design belongs to BRD-031.

---

## Notes

BRD-030 establishes a presentation and asset-delivery boundary, not an authorization boundary.

Its job is deliberately narrow:

```text
Public NOC
    │
    │ minimal silent probe
    ▼
 Bredland reachable?
    │
    ├── no  ──→ ordinary NOC, unchanged
    │
    └── yes
         │
         ▼
 load opaque trusted assets
      from Bredland
         │
         ▼
 subtle trusted-mode presentation
```

The public NOC knows only enough to ask whether Bredland is reachable and, after success, where to obtain the opaque trusted resources.

It does not contain the implementation of trusted mode.

Most importantly:

```text
trusted mode visible ≠ privileged action authorized
```

BRD-031 must independently establish authorization for every privileged operation. Nothing introduced by BRD-030 should need to be trusted as a security control when that work begins.
