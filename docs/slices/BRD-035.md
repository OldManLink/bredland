# 🏗️ BRD-035 — Heartbeat history endpoint

## Status

Planned

## Goal

Add a small read-only NOC endpoint for retrieving stored heartbeat history for a single host.

The endpoint shall expose the canonical heartbeat records already stored by the NOC without interpreting them for any particular client or use case.

The first implementation supports only:

- latest N records;
- bounded time-range queries.

The endpoint provides the history primitive needed by future consumers while preserving the existing architectural principle:

> The NOC owns heartbeat history; clients remain stateless and retrieve history on demand.

---

## Architectural Principle

Heartbeat producers report current facts to the NOC.

The NOC remains the canonical persistent history store.

Consumers that need historical state shall retrieve it from the NOC rather than maintaining an independent local history.

Conceptually:

```text
heartbeat producers
        │
        ▼
       NOC
 canonical history store
        │
        │ read-only history query
        ▼
 Bredland / other consumers
```

Bredland shall not need to maintain a duplicate heartbeat-history database.

---

## Endpoint

Add a dedicated read-only heartbeat-history endpoint.

Requests shall use:

```text
POST
```

The endpoint shall authenticate using the existing host/token model.

A request is scoped to one host.

The authenticated caller shall not gain a general mechanism for browsing arbitrary NOC data.

The exact URL and request representation should follow existing endpoint conventions and be chosen during implementation.

---

## Query Model

The first implementation shall support exactly two query forms.

### Latest N

Retrieve the most recent N stored heartbeat records for the requested host.

Conceptually:

```json
{
  "host": "bredland",
  "query": {
    "latest": 10
  }
}
```

The exact request shape may be refined during implementation.

`N` shall be:

- an integer;
- positive;
- subject to a sensible server-side maximum.

Results shall have deterministic ordering.

---

### Time range

Retrieve stored heartbeat records for the requested host within a bounded time range.

Conceptually:

```json
{
  "host": "bredland",
  "query": {
    "from": 1790000000,
    "to": 1790003600
  }
}
```

The exact representation of timestamps shall be chosen consistently with the existing stored heartbeat format.

The range shall be explicitly bounded.

Unbounded historical scans shall not be supported.

Server-side result limits shall still apply.

Boundary semantics shall be explicit and covered by deterministic tests.

---

## Authentication

Reuse the existing host/token authentication model.

The history endpoint shall not introduce a second authentication system merely for read access.

Authentication and host scoping shall occur before historical data is returned.

Invalid authentication shall reveal no heartbeat history.

The implementation shall preserve the security characteristics of the existing telemetry endpoint where applicable while remaining independently testable.

---

## Canonical Data

Returned records shall represent the canonical heartbeat data stored by the NOC.

The history endpoint shall not perform client-specific interpretation.

It shall not:

- derive health;
- evaluate client Rules;
- generate notifications;
- format values for display;
- translate fields for particular clients;
- calculate graph series;
- infer outages.

Those concerns belong to consumers of the history.

Conceptually:

```text
stored heartbeat
      ↓
history endpoint
      ↓
same heartbeat facts
```

not:

```text
stored heartbeat
      ↓
client-specific interpretation
      ↓
history response
```

---

## Response

Successful requests shall return the matching heartbeat records as JSON.

The response contract shall be deterministic and suitable for programmatic consumers.

Ordering shall be explicitly defined and tested.

Empty valid queries shall return a successful empty result rather than being treated as an endpoint failure.

The endpoint shall preserve the stored heartbeat values and types.

---

## Result Limits

All query forms shall have sensible server-side limits.

The caller shall not be able to request an arbitrarily large history result.

For `latest N`, the requested count shall be bounded directly.

For time-range queries, the endpoint shall enforce a maximum number of returned records even when the requested range contains more data.

Behaviour when a result would exceed the limit shall be explicit and deterministic rather than dependent on incidental filesystem traversal behaviour.

The exact limits may be chosen during implementation and should be easy to change without altering the query model.

---

## Storage Boundary

The endpoint shall read history through the existing NOC heartbeat storage representation.

It shall not introduce a second history store.

Any extraction of a small read-side abstraction from the existing storage code should be driven by the needs of this endpoint and existing code rather than by designing a general persistence framework.

The endpoint must work with the canonical stored heartbeat records, including the existing archive/storage lifecycle where required by the requested range.

---

## TDD / Implementation Sequence

### 1. Characterise stored history

Establish deterministic fixtures representing stored heartbeat history for multiple hosts and timestamps.

Confirm the ordering and timestamp semantics of the canonical stored records before designing the query implementation around them.

---

### 2. Add authenticated endpoint boundary

Add failing tests for the new POST endpoint.

Cover:

- valid authentication;
- missing authentication;
- invalid token;
- invalid host;
- malformed request.

Implement the smallest endpoint boundary necessary to make these tests pass.

No history query capability is required yet.

---

### 3. Implement `latest N`

Add failing tests for retrieving the most recent N records for one host.

Cover at least:

- one record;
- several records;
- fewer stored records than requested;
- no stored records;
- invalid N;
- zero or negative N;
- N exceeding the configured maximum;
- isolation between hosts;
- deterministic ordering.

Implement only enough query/storage behaviour to satisfy this contract.

---

### 4. Implement bounded time ranges

Add failing tests for time-range retrieval.

Cover at least:

- records wholly inside the range;
- records outside the range;
- exact lower boundary;
- exact upper boundary;
- empty range result;
- invalid range;
- reversed range;
- unbounded request;
- result-limit behaviour;
- isolation between hosts;
- deterministic ordering.

Make the boundary semantics explicit through the tests.

---

### 5. Preserve canonical records

Add tests proving that returned heartbeat records preserve the stored data and value types.

The endpoint shall not perform client-specific transformation or Rule evaluation.

---

### 6. Exercise real stored history

Query production history for an existing host using both supported forms.

Verify:

```text
latest N
```

and:

```text
bounded time range
```

against the records already stored by the NOC.

## Out of Scope

- Arbitrary predicates.
- A general query language.
- User-supplied expressions.
- Arbitrary field filtering.
- Arbitrary sorting.
- Aggregation.
- Grouping.
- Graph generation.
- Downsampling.
- Statistical analysis.
- Outage detection.
- Client-specific interpretation.
- Health calculation.
- Rule evaluation.
- Notification generation.
- A Bredland history cache.
- A local Bredland NOC page.
- Heartbeat-history graphs.
- Outage archaeology UI.
- A second history database.

These are consumers or potential extensions of the history primitive, not responsibilities of BRD-035.

---

## Future Predicate Support

A later slice may add simple server-side predicates if a concrete consumer demonstrates the need.

If predicates are added, they shall use a deliberately small whitelist of explicit operators rather than exposing a general query language.

Potential examples might include:

```text
equals
notEquals
lessThan
greaterThan
```

This is intentionally deferred.

BRD-035 should first prove that `latest N` and bounded time ranges provide a clean, useful read boundary over the canonical history store.

---

## Follow-on Uses

The endpoint is expected to enable later slices such as:

- a local Bredland NOC page displaying the last known remote state when the public NOC cannot currently be reached;
- heartbeat-history graphs;
- WAN outage archaeology and diagnostics;
- retrieving recent state around an incident without making Bredland stateful.

These use cases motivate the endpoint but do not belong in this slice.

---

## Notes

The important architectural outcome of BRD-035 is not merely another HTTP endpoint.

It establishes a clean read path back out of the history the NOC already owns:

```text
            POST heartbeat
Bredland ───────────────────► NOC
                               │
                               │ canonical
                               │ history
                               │
Bredland ◄────────────────────┘
          history query
```

That preserves a useful asymmetry:

> NOC is stateful. Clients are not.

A client may temporarily cache a response for presentation or computation, but it does not become another authority for heartbeat history.

The first query vocabulary is deliberately boring:

```text
latest N
time range
```

If outage analysis or graphing later demonstrates that transferring those records and filtering locally is inadequate, we will then have a real use case from which to design the smallest useful predicate extension.

Until then, there is no query language to invent.
