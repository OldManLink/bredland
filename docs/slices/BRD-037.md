# 🏗️ BRD-037 — Extract trusted discovery responsibilities

## Status

Planned

## Goal

Improve the internal structure of `trusted_discovery.template.py` by extracting responsibilities whose boundaries have become visible through the implementation of the trusted-dashboard and trusted-action slices.

This is an architecture-only cleanup.

There shall be **no functional change**.

Existing behaviour shall first be characterised and preserved with tests. Extraction boundaries shall then follow seams already demonstrated by the current code rather than being designed in advance.

---

## Background

`trusted_discovery.template.py` has accumulated responsibilities as the trusted-dashboard architecture has grown through real use cases.

During review of BRD-036, `ActionResultRegistry` and the action-execution workflow were identified as plausible extraction seams.

Other areas that may now represent distinct responsibilities include:

- capability/result/guard execution mechanics;
- HTTP/discovery/asset serving;
- configured wiring;
- state/action selection.

These are areas to investigate, not a prescribed target architecture.

The size of the file alone is not sufficient reason to split it.

The purpose of BRD-037 is to examine the structure that now exists and extract only boundaries that the code has already earned.

---

## Principle

> Extract demonstrated responsibilities; do not design hypothetical ones.

BRD-037 shall begin from the current implementation.

For each proposed extraction, ask:

- Does this code have a coherent responsibility of its own?
- Does it have a meaningful boundary from its neighbours?
- Can that boundary be described without reference to file size?
- Do existing tests demonstrate its contract?
- Does extraction simplify ownership or navigation?
- Would keeping it separate make the next feature easier to place correctly?

If the answer is not convincing, leave the code where it is.

---

## Behaviour Preservation

Before structural changes, establish sufficient characterisation coverage for the behaviour being moved.

The refactoring shall preserve the existing contracts introduced through BRD-030 to BRD-036, including as applicable:

- trusted discovery;
- trusted asset delivery;
- capability selection;
- action guards;
- action validation;
- semantic action selection;
- asynchronous action acceptance;
- request IDs;
- action-result registration and lookup;
- background RouterOS execution;
- result polling;
- configured trusted-server wiring;
- HTTP behaviour.

Tests should move with extracted responsibilities where that improves ownership, but externally observable behaviour shall remain unchanged.

---

## Candidate Seams

### Capability/result/guard execution mechanics

Examine whether the trusted-action execution machinery now forms a coherent unit distinct from HTTP serving and application wiring.

This may include responsibilities around:

- capability execution;
- guards;
- action-result lifecycle;
- `ActionResultRegistry`;
- asynchronous execution workflow.

Do not assume these necessarily belong in one extracted component.

Follow the dependencies already present in the implementation.

---

### HTTP/discovery/asset serving

Examine whether HTTP transport responsibilities form a clear boundary around:

- trusted-network discovery;
- request handling;
- trusted asset serving;
- response construction.

Transport concerns should remain separate from trusted-action domain decisions where the current code demonstrates that distinction.

---

### Configured wiring

Examine the composition/wiring currently performed by `trusted_discovery.template.py`.

Configuration and construction may remain in a thin composition root if that is the clearest ownership model.

Do not objectify configuration merely to reduce line count.

---

### State/action selection

Examine the code responsible for determining which semantic action or state applies to a request.

If this represents a coherent domain responsibility distinct from execution and transport, extract it accordingly.

If the distinction is not yet strong enough, leave it alone.

---

## TDD / Refactoring Sequence

### 1. Establish the baseline

Run the complete test suite and confirm the current BRD-036 implementation is green.

Identify the behaviours currently owned by `trusted_discovery.template.py`.

Record the major dependency directions before changing structure.

---

### 2. Strengthen characterisation tests where necessary

Before moving a responsibility, ensure its existing behaviour is adequately protected.

Add tests only where the current coverage is insufficient to refactor safely.

These tests shall characterise existing behaviour rather than introduce new requirements.

---

### 3. Identify the first demonstrated seam

Choose the clearest responsibility already visible in the code.

`ActionResultRegistry` and/or the action-execution workflow are known candidates from BRD-036 review, but they are not mandatory first extractions.

Select based on the actual current dependency structure.

---

### 4. Extract one responsibility

Move only the selected responsibility.

Keep the change mechanical where possible.

Run its focused tests and the complete suite.

Do not combine extraction with behavioural improvement.

---

### 5. Reassess the remaining file

After each extraction, inspect `trusted_discovery.template.py` again.

The removal of one responsibility may make the next boundary clearer — or demonstrate that no further extraction is warranted.

Do not commit in advance to a particular number of resulting modules/classes.

---

### 6. Repeat only for earned boundaries

Extract further responsibilities only when their ownership is now clear and tests protect their contracts.

Potential areas include:

```text
execution mechanics
HTTP/discovery/assets
configured wiring
state/action selection
```

but the implementation is not required to produce one component for each item.

---

### 7. Verify the resulting composition

Confirm that `trusted_discovery.template.py` has a clearer remaining responsibility.

It may appropriately remain as a composition root and/or trusted-server entry point.

The goal is not to empty the file.

The goal is that each remaining responsibility has an obvious reason to be there.

## Notes

This slice exists because several real trusted-dashboard features have now passed through the same implementation, giving us enough evidence to see responsibilities that were not obvious when BRD-030 began.

The desired progression is:

```text
working code
    ↓
real features accumulate
    ↓
responsibilities become visible
    ↓
tests preserve behaviour
    ↓
extract demonstrated seams
```

not:

```text
large file
    ↓
invent target architecture
    ↓
force existing code into it
```

BRD-037 therefore deliberately does not prescribe the final module or class structure.

A successful result may involve several extractions.

It may equally reveal that only one or two responsibilities deserve separation today.

The quality criterion is not the final line count of `trusted_discovery.template.py`.

It is whether a future feature has a clearer answer to:

> Where does this responsibility belong?
