# BRD-020 — Harden PHP error handling 🔐

## Status

Completed

## Goal

Prevent PHP from exposing implementation details to HTTP clients while preserving complete diagnostic information for developers.

The NOC should never reveal internal filesystem paths, source locations, PHP version behaviour, stack traces, or other implementation details in browser responses. Instead, PHP errors should be logged privately and HTTP clients should receive only generic error responses.

This slice hardens the production PHP environment without reducing diagnostic visibility for developers.

---

## Design

### Error display

Configure the production PHP environment so that PHP errors are never displayed to HTTP clients.

This includes:

- runtime errors;
- startup errors;
- warnings;
- notices;
- parse errors.

---

### Error logging

Enable comprehensive PHP error logging.

The configuration shall:

- enable `log_errors`;
- use `error_reporting = E_ALL`;
- write logs to a directory outside the web root, for example:

```text
/home/arcanel/web_safe/noc/errors/
```

Developers should retain complete diagnostic information while clients receive only generic responses.

---

### Deployment

Document the chosen configuration mechanism.

Examples include:

- `.user.ini`
- cPanel MultiPHP INI Editor
- another equivalent hosting-supported mechanism

The documented approach shall be reproducible on a fresh deployment.

---

## Acceptance Criteria

- [ ] `display_errors = Off`
- [ ] `display_startup_errors = Off`
- [ ] `log_errors = On`
- [ ] `error_reporting = E_ALL`
- [ ] `error_log` points to a private directory outside `public_html`.
- [ ] PHP warnings are no longer visible via browser, browser developer tools, or `curl`.
- [ ] PHP parse errors are no longer visible via browser, browser developer tools, or `curl`.
- [ ] PHP errors continue to be written to the private log.
- [ ] The chosen configuration method is documented.

---

## Notes

This slice hardens error handling only.

It does not change application behaviour, logging format, or exception handling.

The objective is to eliminate information disclosure while preserving full diagnostic capability for development and operational troubleshooting.
