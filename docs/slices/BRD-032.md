# 🔐 BRD-032 — First trusted dashboard action

## Status

Planned

## Goal

Prove the complete trusted-action path by allowing an available MikroTik RouterOS update to be installed from its existing NOC notification.

This slice introduces exactly one privileged dashboard action:

> Install the available RouterOS update.

The public NOC remains observational. It may carry inert semantic metadata describing how a notification can be resolved, but it shall contain no privileged UI, action implementation, RouterOS command, or authorization logic.

Trusted presentation and interaction remain the responsibility of assets served by Bredland.

Authorization, validation and execution remain independently enforced by Bredland and the trusted management network.

This is a proof of concept for one real action, not the beginning of a generic action framework.

---

## Architectural Principle

The complete path is:

```text
Rule
  ↓
semantic resolution
  ↓
Notification
  ↓
inert data-resolution metadata
  ↓
Bredland-served trusted.js
  ↓
trusted action button
  ↓
explicit confirmation
  ↓
semantic request to Bredland
  ↓
Bredland validates and maps resolution
  ↓
restricted RouterOS REST account
  ↓
explicitly provisioned privileged script
  ↓
RouterOS operation
```

Every boundary shall remain independently meaningful.

In particular:

```text
data-resolution ≠ authorization
trusted UI visible ≠ authorization
browser request ≠ permission to execute
```

Bredland owns the decision about whether a requested resolution is known, permitted and currently reasonable to execute.

## Design

### Notification resolution

Extend the existing Rule notification argument with an optional semantic `resolution`.

For example:

```json
{
  "when": {
    "...": "..."
  },
  "then": {
    "receiver": "client",
    "method": "addNotification",
    "argument": {
      "text": "RouterOS {{latest_version}} is available on the {{update_channel}} channel.",
      "resolution": "install-routeros-update"
    }
  }
}
```

The exact surrounding rule syntax shall follow the existing client-description contract.

`resolution` describes the semantic outcome available for a notification.

It does not describe:

- a RouterOS command;
- a RouterOS script name;
- an HTTP endpoint;
- implementation details of the action.

The resolution shall be preserved through the existing notification model/compiler path.

---

### Notification markup

When a notification has a resolution, `NotificationPanel` shall expose it as inert semantic metadata.

For example:

```html
data-resolution="install-routeros-update"
```

When a notification has no resolution, no `data-resolution` attribute shall be rendered.

The public dashboard shall not interpret this value.

It shall not:

- render an action button;
- attach privileged behaviour;
- know which resolutions are supported;
- map resolutions to actions;
- contain RouterOS action implementation.

The metadata is part of the notification's semantic representation, not an authorization mechanism.

---

### Trusted enhancement

The Bredland-served `trusted.js` introduced by BRD-030 shall recognise the resolution supported by this slice.

When it encounters a notification carrying that resolution, trusted JavaScript shall enhance the notification with an appropriate action button.

Notifications without a supported resolution remain unchanged.

The privileged UI therefore exists only in the trusted asset delivered by Bredland.

---

### Explicit confirmation

Clicking the trusted action button shall not immediately perform the disruptive operation.

The user must explicitly confirm the action before the request is sent for execution.

Cancelling confirmation shall perform no action.

The confirmation should make the intended operation sufficiently clear that an accidental click cannot silently initiate a RouterOS update and reboot.

---

## Trusted Action Request

After confirmation, `trusted.js` shall send the semantic resolution to Bredland.

Conceptually:

```text
install-routeros-update
```

The browser shall not supply:

- arbitrary RouterOS commands;
- RouterOS script names;
- REST paths chosen by the browser;
- shell commands;
- implementation details controlling how the resolution is executed.

The browser asks Bredland to resolve a semantic outcome.

Bredland decides whether and how that outcome may be performed.

---

## Bredland Resolution Mapping

Bredland shall contain the explicit mapping between the supported semantic resolution and its permitted implementation.

For this slice there shall be exactly one production mapping:

```text
install-routeros-update
        ↓
approved RouterOS update operation
```

Unknown, malformed or unsupported resolutions shall be rejected.

The implementation shall not introduce a generic browser-controlled command dispatcher.

---

## Independent Validation

Receiving a recognised resolution is not sufficient reason to execute it.

Before crossing the privileged boundary, Bredland shall independently determine that the requested action is still reasonable and current.

For the RouterOS update action, this shall include sufficient validation to prevent a stale or fabricated browser request from blindly causing an update operation.

The validation shall rely on trusted information available to Bredland rather than treating browser-supplied state as authoritative.

Failure of validation shall reject the action cleanly without invoking the privileged RouterOS script.

---

## RouterOS Execution Boundary

### Restricted REST account

Bredland shall access RouterOS HTTPS REST using a dedicated account provisioned specifically for the NOC action path.

The account shall be source-restricted to Bredland's trusted-network IP.

The feasibility spike established the minimum policies required for the intended REST read access as:

```text
read,api,rest-api
```

The production account shall not possess generic REST write authority.

The credential shall remain private to Bredland and shall not be exposed to:

- the public NOC;
- public JavaScript;
- trusted JavaScript;
- browser requests.

---

### Privileged RouterOS scripts

Privilege shall live in narrowly scoped, explicitly provisioned RouterOS scripts rather than in the Bredland REST credential.

The feasibility spike demonstrated that a deliberately provisioned script using:

```text
dont-require-permissions=yes
```

can be invoked by the restricted REST account even though that account cannot otherwise perform the privileged operation.

For this slice, only explicitly approved scripts shall cross that boundary.

The browser shall never choose the script name.

Bredland shall map the semantic resolution to the known, provisioned script internally.

---

## Harmless End-to-End Test Action

Almost the entire trusted-action chain shall initially be developed and verified using a harmless RouterOS test action.

The test script shall have an obvious and deterministic side effect, such as writing a distinctive entry to the RouterOS log.

This shall prove the complete path:

```text
Rule
  ↓
data-resolution
  ↓
trusted.js
  ↓
trusted button
  ↓
confirmation
  ↓
Bredland
  ↓
restricted REST user
  ↓
approved test script
  ↓
observable RouterOS result
```

The real RouterOS updater shall not be used while this plumbing is being developed.

---

## RouterOS Update-Check Provisioning

The existing nightly RouterOS update-check script and scheduler are dependencies of the update-notification behaviour used by BRD-032.

Bring their provisioning under repository management as part of this slice.

The repository-managed provisioning shall ensure that the required update-check script and scheduler can be installed and verified reproducibly rather than depending on manually maintained RouterOS state.

This work shall preserve the existing update-check behaviour; redesigning that behaviour is not part of BRD-032.

```text

```

---

### 11. Provision the real update script

Provision the deliberately privileged RouterOS script:

```text

```

---

### 12. Perform the real action

From trusted dashboard mode:

1. open the existing RouterOS update notification;
2. press the trusted update button;
3. explicitly confirm the operation;
4. observe the router initiate the update and reboot;
5. wait for telemetry to resume;
6. verify that the reported installed version is the expected new version;
7. verify that the update notification disappears.

This real update is deliberately the final end-to-end acceptance test.

## Security Invariants

The following are requirements of the architecture, not merely implementation details:

- The public NOC remains observational.
- `data-resolution` is inert metadata, not authorization.
- Trusted-mode presentation is not authorization.
- Spoofing trusted UI grants no authority.
- Fabricating a resolution grants no authority.
- Browser-supplied state is not authoritative.
- The browser never supplies RouterOS commands or script names.
- Bredland owns the semantic resolution-to-action mapping.
- Bredland independently validates each requested execution.
- The RouterOS REST credential has no generic write authority.
- RouterOS privilege resides only in deliberately provisioned, narrowly scoped scripts.
- Only explicitly provisioned scripts may cross the privileged boundary.

## Out of Scope

- Additional trusted actions.
- A generic action framework.
- Generic action registries.
- Browser-selectable RouterOS commands.
- Browser-selectable RouterOS script names.
- Generic command queues.
- General remote shell capability.
- A broad Bredland control API.
- Permanent general-purpose privileged credentials.
- Treating trusted-mode discovery as authorization.
- Treating `data-resolution` as authorization.
- Automatic execution without explicit user confirmation.
- Redesigning the notification UI.
- Redesigning RouterOS update checking.
- General RouterOS administration from the NOC.

## Notes

BRD-030 established that the public NOC may discover trusted mode while keeping the trusted implementation on Bredland.

BRD-032 crosses the next boundary deliberately and narrowly:

> Can one semantic notification resolution safely become one explicitly authorised local action?

The answer should be demonstrated with the smallest possible chain.

For most of the slice, that chain terminates in a harmless, observable RouterOS test script.

Only after every preceding boundary has been exercised successfully do we substitute the real operation.

The browser's request remains intentionally boring:

```text
install-routeros-update
```

It does not know that this ultimately maps to:

```text
noc-install-routeros-update
```

That knowledge belongs to Bredland.

Likewise, the Bredland credential itself does not carry general RouterOS write privilege. The exceptional privilege resides in one deliberately provisioned and auditable RouterOS script.

This gives the proof of concept several independent layers of containment:

```text
semantic resolution
        ↓
Bredland allow-list + validation
        ↓
restricted REST identity
        ↓
explicit privileged script
        ↓
one intended RouterOS operation
```

BRD-032 should prove that model with exactly one real action.

If the model later deserves generalisation, subsequent slices can earn that abstraction from additional concrete use cases.
