# 🍕 BRD-039 — Preserve OSM share counters

## Status

Planned

## Goal

Preserve the One Shot Miner's cumulative accepted and rejected Stratum share counters in its ordinary NOC heartbeat.

Add two integer telemetry fields:

```text
shares_accepted
shares_rejected
```

sourced from the OSM API's cumulative:

```text
sAccepted
sRejected
```

Keep the heartbeat factual.

Do not calculate acceptance percentages, derive deltas, infer health, or interpret rejected shares as an outage condition.

---

## Background

A WAN outage demonstrated a small gap in the OSM telemetry introduced by BRD-018.

The miner remained powered, running and hashing throughout the outage.

After connectivity recovered, its Stratum statistics showed:

```text
210 accepted
2 rejected
99.1% accepted
```

The rejected shares were useful evidence of what had happened while WAN connectivity was unavailable.

However, because the cumulative accepted/rejected counters were not included in the OSM heartbeat, that evidence was visible only in the miner's current state.

Had the counters been preserved in ordinary heartbeat history, later queries could identify when the cumulative values changed and correlate those changes with other telemetry such as MikroTik WAN state.

BRD-039 closes that telemetry gap.

---

## Principle

> Preserve facts now; derive meaning later.

The OSM already knows two useful cumulative facts:

```text
accepted shares
rejected shares
```

The heartbeat should preserve those facts.

Consumers can later derive:

- counter deltas;
- acceptance percentages;
- rejection rates;
- time correlations;
- relationships with WAN outages or recovery.

Those interpretations do not belong in the producer heartbeat.

---

## Telemetry

Add:

```text
shares_accepted
shares_rejected
```

as integer fields in the OSM heartbeat.

Their source values are:

```text
miner.sAccepted
miner.sRejected
```

from the existing OSM telemetry response.

The collector shall normalize them through the same mechanism used by the other BRD-018 OSM fields.

No special storage or transport behaviour is required.

---

## Historical Semantics

The values are cumulative counters reported by the miner.

Each heartbeat therefore records the counter state observed at that moment.

For example:

```text
timestamp    shares_accepted    shares_rejected
------------------------------------------------
10:00        208                0
10:05        209                0
10:10        209                2
10:15        210                2
```

The heartbeat does not explain why a counter changed.

It merely preserves that it changed.

A later consumer may correlate the change with other historical telemetry.

---

## Rendering

Expose both fields through the existing self-describing OSM client configuration.

Use the ordinary generic rendering path.

No OSM-specific dashboard code is required.

No acceptance percentage needs to be displayed as part of this slice.

## Notes

BRD-018 established the OSM as an ordinary first-class NOC client.

BRD-039 adds two more facts to that existing path.

The motivating WAN incident demonstrated why cumulative counters are worth preserving even when no immediate alert or display logic is required.

A future history query should be able to answer:

```text
When did shares_rejected change?
```

and then compare that timestamp with other independently recorded facts.

The heartbeat itself need know nothing about that interpretation.

This is deliberately a tiny slice:

```text
OSM API
   ↓
sAccepted / sRejected
   ↓
integer normalization
   ↓
ordinary heartbeat
   ↓
ordinary history
```

Everything after extraction already exists.
