# 🔐 BRD-033 — RouterBOOT firmware update action

## Status

Planned

## Goal

Detect when the MikroTik has a RouterBOOT firmware update pending and allow that update to be performed as a distinct trusted dashboard action.

RouterOS package updates and RouterBOOT firmware updates represent different device states and require different operations.

After a RouterOS update, the router may report state such as:

```text
current-firmware: 7.23.1
upgrade-firmware: 7.24.2
```

BRD-033 shall expose that state through normal telemetry, derive a distinct notification using the existing Rule architecture, and provide a separately authorised trusted action for installing the RouterBOOT firmware update.

This is the second concrete use case for the trusted-action architecture introduced by BRD-032.

---

## Principles

- Heartbeats contain facts.
- Client descriptions derive behaviour from facts.
- RouterOS package state and RouterBOOT firmware state remain distinct.
- Each privileged operation has its own semantic resolution.
- Browser-visible resolution metadata is not authorization.
- Bredland independently validates every privileged request.
- RouterOS privilege remains confined to narrowly scoped, explicitly provisioned scripts.
- Common trusted-action abstractions shall emerge only where BRD-032 and BRD-033 demonstrate genuine repetition.

---

## Telemetry

Add RouterBOARD firmware state to the MikroTik heartbeat.

The heartbeat shall include separate fields representing:

- the currently installed RouterBOOT firmware version;
- the RouterBOOT firmware version available for upgrade.

For example:

```json
{
  "current_firmware": "7.23.1",
  "upgrade_firmware": "7.24.2"
}
```

The exact field names shall remain concise and consistent with the existing MikroTik telemetry vocabulary.

The heartbeat schema and client description shall be updated accordingly.

No derived `firmware_update_available` boolean is required.

The heartbeat contains the firmware facts; the Rule determines whether they require attention.

---

## RouterBOOT Update Rule

Add a MikroTik Rule that compares the current and upgrade RouterBOOT firmware versions.

Conceptually:

```text
current_firmware != upgrade_firmware
```

When the versions differ, the Rule shall emit a distinct notification indicating that a RouterBOOT firmware update is pending.

For example:

```text
RouterBOOT firmware 7.24.2 is available.
```

The notification shall have its own semantic resolution, separate from the RouterOS package-update resolution introduced by BRD-032.

For example:

```text
install-routerboot-update
```

The exact semantic name may be refined during implementation, but it shall represent the intended outcome rather than a RouterOS command or script name.

---

## Notification Presentation

The existing notification and trusted-mode mechanisms shall be reused.

The public NOC may render the semantic resolution as inert notification metadata through the mechanism introduced by BRD-032.

The public NOC shall not:

- interpret the RouterBOOT resolution;
- render the trusted action button;
- know which RouterOS command implements the action;
- know the privileged RouterOS script name;
- contain RouterBOOT-specific action logic.

Bredland-served trusted JavaScript shall recognise the supported RouterBOOT resolution and enhance the notification with the appropriate trusted action control.

The RouterBOOT notification and action shall remain distinct from the RouterOS package-update notification and action.

---

## Explicit Confirmation

The RouterBOOT action shall require explicit confirmation before execution.

The confirmation shall make clear that the operation updates RouterBOOT firmware and requires the router to reboot.

Cancelling confirmation shall perform no privileged request.

---

## Bredland Validation

After confirmation, trusted JavaScript shall send only the semantic RouterBOOT resolution to Bredland.

Bredland shall independently inspect the live RouterBOARD state before executing anything privileged.

Execution shall proceed only when Bredland confirms that a RouterBOOT upgrade is still genuinely pending.

Conceptually:

```text
current-firmware != upgrade-firmware
```

If the state is already current, unavailable, malformed, or otherwise inconsistent with the requested action, Bredland shall reject the request without invoking the privileged RouterOS operation.

Browser-supplied firmware versions shall not be authoritative.

---

## RouterOS Execution

Bredland shall map the RouterBOOT semantic resolution to one explicitly approved RouterOS operation.

The browser shall never provide:

- `/system routerboard upgrade`;
- a RouterOS script name;
- arbitrary RouterOS commands;
- arbitrary REST paths.

The privileged RouterOS boundary shall follow the least-privilege mechanism established by BRD-032:

```text
semantic resolution
        ↓
Bredland mapping + live validation
        ↓
restricted RouterOS REST account
        ↓
explicitly provisioned privileged script
        ↓
RouterBOOT upgrade + required reboot
```

The privileged script shall perform only the RouterBOOT update operation required by this slice.

---

## Second-Use-Case Refactoring

BRD-033 is deliberately the second concrete trusted action.

During implementation, compare its needs with the implementation produced by BRD-032.

Where both actions demonstrate genuine identical behaviour, small common abstractions may be extracted.

Do not introduce generality merely because additional trusted actions can be imagined.

In particular, this slice shall not grow into:

- a generic command framework;
- a general RouterOS administration API;
- a generic browser-controlled action registry;
- a command queue;
- a general-purpose privileged script launcher.

Any refactoring shall be justified by actual duplication between the two implemented actions.

### 5. Add independent Bredland validation

Drive the Bredland boundary with tests covering at least:

- genuine pending RouterBOOT update;
- firmware already current;
- unavailable or malformed live state;
- unsupported/fabricated resolution;
- RouterOS communication failure.

---

### 6. Provision the privileged RouterOS operation

Provision the narrowly scoped RouterOS script required to perform:

```text
/system routerboard upgrade
```

and the required reboot.

Use the restricted RouterOS execution path established by BRD-032.

Verify that the browser cannot choose the script or command being executed.

---

### 7. Review actual duplication

Compare the BRD-032 and BRD-033 trusted-action implementations.

Extract only those common pieces for which two real implementations now provide evidence.

Keep action-specific validation and privileged behaviour explicit.

---

### 8. Perform the real action

From trusted dashboard mode:

1. confirm telemetry reports differing current and upgrade RouterBOOT firmware versions;
2. confirm the RouterBOOT notification is visible;
3. open the notification;
4. press its trusted action button;
5. explicitly confirm the RouterBOOT update;
6. observe the upgrade and required router reboot;
7. wait for telemetry to resume;
8. verify that the current RouterBOOT firmware now matches the upgrade firmware;
9. verify that the RouterBOOT notification disappears.

## Notes

BRD-032 proves the first trusted action using a RouterOS package update.

BRD-033 deliberately treats RouterBOOT firmware as a second independent state and operation.

That distinction matters operationally:

```text
RouterOS package current
          ≠
RouterBOOT firmware current
```

A successful RouterOS package update may therefore expose a second piece of work rather than completing the entire router update process.

Architecturally, BRD-033 also gives us something valuable that BRD-032 could not:

> repetition.

If the two implementations reveal genuinely common trusted-action behaviour, we now have evidence from which to extract it.

If they differ, we preserve those differences rather than forcing them through an abstraction designed around a single example.

The sequence remains intentionally explicit:

```text
heartbeat facts
      ↓
declarative Rule
      ↓
semantic resolution
      ↓
trusted presentation
      ↓
explicit confirmation
      ↓
Bredland live validation
      ↓
narrow privileged boundary
      ↓
one RouterBOOT operation
      ↓
telemetry proves the result
```

The final authority remains reality reported by the router: once telemetry says the current and upgrade RouterBOOT firmware versions match, the condition becomes false and the notification disappears naturally.
