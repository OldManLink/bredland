# 🍕 BRD-034 — Monitor Bredland TLS certificate expiry

## Status

Planned

## Goal

Monitor the expiry of Bredland's TLS certificate through the existing heartbeat and raise a persistent NOC notification before the certificate expires.

This slice monitors the deadline only.

Certificate renewal remains a manual operational action for now.

> Monitor the deadline now; automate the remedy later.

---

## Background

The TLS certificate expiry is readily available from the certificate installed on Bredland.

A feasibility spike performed on 2026-09-13 proved that the expiry can be derived locally from the actual PEM using standard tooling:

```bash
sudo openssl x509 -in <cert.pem> -noout -enddate \
  | cut -d= -f2- \
  | xargs -I{} date -d '{}' +%s
```

The live certificate reported:

```text
notAfter=Nov 23 17:52:58 2026 GMT
```

which produced:

```text
1795456378
```

This gives the heartbeat producer a simple absolute deadline that requires no certificate parsing by the NOC.

---

## Design

### Heartbeat fact

Add a Bredland heartbeat field:

```text
tls_cert_expires_at
```

Its value shall be the certificate expiry as an absolute Unix timestamp in seconds.

For example:

```json
{
  "tls_cert_expires_at": 1795456378
}
```

The value shall be derived locally from the actual certificate used by Bredland.

The heartbeat producer shall not calculate:

- days remaining;
- warning state;
- expiry severity;
- whether a notification should exist.

It reports only the certificate's absolute expiry deadline.

---

## Schema and client description

Add `tls_cert_expires_at` to the Bredland heartbeat schema with the appropriate integer value type.

Expose the field through the Bredland client description as required by the existing self-describing-client contract.

The representation shall remain an absolute timestamp rather than a precomputed relative duration.

---

## Expiry Rule

Add a declarative Rule that compares the certificate expiry deadline with the current NOC time.

The Rule shall create a persistent notification when the remaining certificate lifetime falls below the chosen warning threshold.

Initial intended threshold:

```text
21 days
```

Conceptually:

```text
tls_cert_expires_at - now < 21 days
```

The exact Rule representation should use the existing rule/compiler architecture, extending generic time comparison capability only as much as is required.

No Bredland-specific conditional logic shall be added to dashboard PHP.

---

## Notification

When the certificate enters the warning window, emit a notification indicating that manual TLS certificate renewal is required.

The notification should make the expiry deadline clear enough for the operator to act before service is affected.

No semantic `resolution` is required in this slice.

The notification therefore remains informational and observational.

After the certificate is manually renewed:

1. Bredland reads the new certificate;
2. the next heartbeat reports the new `tls_cert_expires_at`;
3. the Rule condition becomes false;
4. the notification disappears naturally.

No acknowledgement or explicit clearing mechanism is required.

---

## Manual Renewal

Automatic certificate renewal is explicitly deferred.

Current investigation indicates that Oderland cannot provide an API token scoped narrowly enough to make unattended ACME/DNS renewal acceptable.

For now, renewal shall therefore remain manual.

A likely operational workflow is:

1. run Certbot on Bredland;
2. maintain an authenticated SSH session to Oderland;
3. add the required `_acme-challenge` TXT record using available cPanel CLI tooling;
4. complete the ACME challenge;
5. remove the temporary TXT record;
6. install/reload the renewed certificate;
7. verify that the next Bredland heartbeat reports the new expiry timestamp.

The exact Oderland/cPanel commands shall be investigated when implementing or documenting the manual renewal procedure.

They are not part of the monitoring architecture.

## Notes

The expiry timestamp is deliberately an absolute fact:

```text
tls_cert_expires_at = 1795456378
```

rather than producer-derived state such as:

```text
days_remaining = 71
certificate_expiring = false
```

That keeps responsibility aligned with the existing architecture:

```text
Bredland
   ↓
reports certificate deadline
   ↓
NOC Rule + current time
   ↓
derives whether attention is required
   ↓
persistent notification
```

Renewing the certificate changes the fact at the source. No special notification lifecycle is necessary.

For the current certificate:

```text
expiry:          2026-11-23 17:52:58 UTC
21-day warning:  approximately 2026-11-02
```

BRD-034 should therefore be completed comfortably before the beginning of November 2026.
