# 🍕 BRD-034 — Monitor Bredland TLS certificate expiry

## Status

Completed

## Goal

Monitor the expiry of Bredland's TLS certificate through the existing heartbeat and raise a persistent NOC notification before the certificate expires.

Certificate renewal remains a manual operational action for now.

> Monitor the deadline now; automate the remedy later.

---

## Background

Bredland serves trusted-dashboard HTTPS using a locally installed TLS certificate.

A feasibility spike performed on 2026-09-13 proved that the expiry can be derived locally from the actual PEM using standard tooling:

```bash
sudo openssl x509 -in <cert.pem> -noout -enddate \
  | cut -d= -f2- \
  | xargs -I{} date -d '{}' +%s
```

The certificate observed during the spike reported:

```text
notAfter=Nov 23 17:52:58 2026 GMT
```

which corresponds to the Unix timestamp:

```text
1795456378
```

That spike established that Bredland can reliably derive the expiry from the real installed certificate.

The final telemetry design deliberately does **not** transmit that absolute timestamp.

Instead, Bredland reports the remaining certificate lifetime in seconds.

## Design

### Heartbeat fact

The Bredland heartbeat reports:

```text
tls_cert_remaining
```

Its value is:

```text
certificate_expiry_epoch - current_epoch
```

The installed certificate is read from:

```text
/etc/bredland/tls/fullchain.pem
```

Semantics:

```text
valid future certificate
→ positive integer seconds remaining

certificate unreadable or OpenSSL/parsing failure
→ 0

genuinely expired certificate
→ negative integer seconds remaining
```

Negative values are deliberately **not clamped to zero**.

This lets the heartbeat distinguish:

```text
0
```

meaning:

> expiry could not be determined

from:

```text
< 0
```

meaning:

> the certificate is genuinely expired

The heartbeat producer does not calculate:

- warning state;
- expiry severity;
- whether a notification should exist.

Those remain NOC concerns.

---

## Heartbeat privilege model

The Bredland heartbeat service runs as:

```ini
User=bredland-trusted
Group=bredland-trusted
```

Shared provisioning of the `bredland-trusted` user/group is provided by:

```text
scripts/lib/bredland.sh
```

The shared helper creates only the common user/group.

Individual consumers retain responsibility for their own additional privilege requirements.

For the heartbeat deployment, `bredland-trusted` is additionally granted the required group membership.

The heartbeat remains a `Type=oneshot` systemd service, so after a successful execution:

```text
inactive (dead)
status=0/SUCCESS
```

is the expected healthy state.

## Heartbeat tests

Dedicated heartbeat coverage exists in:

```text
tests/sh/bredland-heartbeat.test.sh
```

Run through the normal test runner:

```bash
./tests/run-all.sh 'sh:bredland-heartbeat'
```

The suite verifies:

1. a valid future certificate produces the expected positive `tls_cert_remaining`;
2. OpenSSL/certificate failure produces `tls_cert_remaining=0`;
3. an expired certificate preserves a negative value.

The test harness uses fake commands through `PATH` and captures heartbeat POST data through a fake `curl`.

Repeated curl argument checks are handled by:

```text
assert_curl_argument()
```

## Schema and client description

`tls_cert_remaining` is declared as an integer heartbeat field.

The Bredland client description exposes it through the existing self-describing-client contract.

The representation remains ordinary telemetry:

```json
{
  "tls_cert_remaining": 1234567
}
```

No certificate-specific dashboard PHP is required.

## Expiry Rule

The NOC uses the existing generic `lessThan` Rule operator.

No new deadline/current-time comparison machinery was required.

Current warning threshold:

```text
30 days
```

which is:

```text
2592000 seconds
```

Conceptually:

```text
tls_cert_remaining < 2592000
```

The 30-day threshold is deliberate.

Renewal of Bredland's certificate is manual, so there is no automatic renewal process that would make a 30-day warning noisy or transient.

A full month of warning gives the operator useful time to perform the renewal and recover from any DNS/ACME problems without creating unnecessary urgency.

## Notification

When the certificate enters the warning window, the NOC emits an informational notification containing the actual remaining lifetime.

The rule uses the normal value/formatter machinery:

```json
{
  "when": {
    "field": "tls_cert_remaining",
    "operator": "lessThan",
    "value": 2592000
  },
  "then": {
    "receiver": "client",
    "method": "addNotification",
    "argument": {
      "text": [
        "Bredland TLS certificate expires in ",
        {
          "field": "tls_cert_remaining",
          "formatter": "display_duration"
        }
      ]
    }
  }
}
```

No semantic `resolution` is required.

The notification remains informational and observational.

A local preview fixture deliberately uses the non-round value:

```text
1234567
```

seconds.

This renders as:

```text
Bredland TLS certificate expires in 2w0d06:56:07
```

Using an awkward value provides a useful end-to-end proof that the displayed duration is derived from heartbeat telemetry rather than leaking a Rule threshold or another constant.

After the certificate is manually renewed:

1. Bredland reads the new certificate;
2. the next heartbeat reports a larger `tls_cert_remaining`;
3. the Rule condition becomes false;
4. the notification disappears naturally.

No acknowledgement or explicit clearing mechanism is required.

## Formatter naming

The existing formatter:

```text
display_uptime
```

was found to be incorrectly named because it formats an arbitrary duration in seconds rather than specifically an uptime.

It was renamed globally to:

```text
display_duration
```

Its formatting semantics were not changed as part of the rename.

## Compiler cleanup driven by BRD-034

Displaying a formatted heartbeat value inside a notification exposed two pieces of old compiler magic:

1. notification interpolation using embedded `{{field}}` syntax;
2. positional notification arguments using `[text, resolution]`.

Rather than adding a notification-specific formatting mechanism, the compiler was simplified so that formatted values compose normally everywhere.

### NotificationVal

The old positional forms were removed.

Notification arguments now use explicit named structure:

```json
{
  "text": [
    "Software update available"
  ]
}
```

or:

```json
{
  "text": [
    "Software update available: ",
    {
      "field": "latest_version"
    }
  ],
  "resolution": "install-routeros-update"
}
```

Conceptually:

```text
NotificationVal
├── text       → SlotVal
└── resolution → Option<StrVal>
```

`NotificationVal` uses `PartCompiler`.

---

## Option

A deliberately small `Option` abstraction was added.

Internal representation:

```text
None    = []
Some(x) = [x]
```

Supported operations currently include:

```text
map()
get_or_else()
values()
```

Only operations required by real compiler pressure have been added.

No nullable optional compiler values are required.

---

## PartCompiler

`PartCompiler` now supports required and optional named parts.

Contract:

```text
required + present
→ compiled value

required + missing
→ compilation failure

optional + present
→ Option::some(compiled value)

optional + missing
→ Option::none()
```

`partClasses()` is the source of truth for legal parts.

`optionalParts()` declares exceptions:

```php
private static function optionalParts() {
    return array(
        'resolution' => true
    );
}
```

`PartCompiler` also validates:

```text
outer definition is an object
present key has a valid identifier
present key is a declared part
required part is present
```

This preserves useful diagnostics such as:

```text
Field.value: invalid identifier: fiéld
```

rather than allowing invalid keys to degrade into misleading "missing part" errors.

---

## SlotVal

The old interpolation mini-language has been removed.

There is no longer any:

```text
{{field}}
```

parsing.

`SlotVal` is now an explicit array of ordinary `Val` definitions.

Example:

```json
[
  "Software update available: ",
  {
    "field": "latest_version"
  }
]
```

Compilation is simply:

```text
SlotVal
→ Val::compile() for each element
```

Runtime rendering remains ordinary concatenation of the resulting runtime values.

The obsolete `SlotPart` interface was removed.

`StrVal` and `FieldVal` now implement the ordinary runtime-value contract directly.

---

## FormatterVal

Object-valued `Val` definitions now compile through:

```text
FormatterVal
```

rather than directly through `FieldVal`.

Supported syntax:

```json
{
  "field": "uptime"
}
```

or:

```json
{
  "field": "uptime",
  "formatter": "display_duration"
}
```

Conceptually:

```text
FormatterVal
├── FieldVal
└── Option<FormatVal>
```

`FormatterVal` owns:

- source field compilation;
- optional formatter compilation;
- formatter/value-type compatibility;
- runtime formatter application;
- runtime type safety;
- delegation of the underlying schema value type.

A formatter incompatible with the source field type fails compilation.

A runtime value inconsistent with the declared schema type renders as:

```text
unavailable
```

When no formatter is supplied, the raw field value is rendered.

---

## Val

Object dispatch changed from:

```text
object → FieldVal
```

to:

```text
object → FormatterVal
```

This means cards, notifications, predicates, and any other value context share the same value syntax automatically.

No notification-specific formatter language exists.

---

## Field

Dashboard `Field` objects no longer own formatter mechanics.

The old structure:

```text
label
field
format
```

became:

```text
label
value
```

where:

```text
value → FormatterVal
```

Example:

```json
{
  "label": "Uptime",
  "value": {
    "field": "uptime",
    "formatter": "display_duration"
  }
}
```

`Field` delegates rendering to `FormatterVal`.

It retains access to the underlying `FieldVal` where required by `FieldList` for indexing and duplicate-source-field detection.

There is now one formatter/value syntax throughout the compiler.

## Compiler architecture after BRD-034

```text
Action
  ReceiverVal
    MethodVal
      argument class
        NotificationVal / HealthVal / BoolVal

NotificationVal
  SlotVal
  Option<StrVal>

SlotVal
  Val*

Val
  primitive → existing scalar Vals
  object    → FormatterVal

FormatterVal
  FieldVal
  Option<FormatVal>

Field
  StrVal label
  FormatterVal value

FieldList
  indexes/rejects duplicate source fields through Field
```

Removed compiler magic:

```text
{{}} interpolation parser          → deleted
SlotPart                           → deleted
notification positional array     → deleted
Field-owned formatter logic       → moved into FormatterVal
context-specific formatter syntax → eliminated
```

## Test-framework improvement

During migration of stale compiler tests, boolean assertion failures were difficult to locate because an unlabelled `assertTrue()` only produced:

```text
Expected: true
Actual:   false
```

`assertTrue()` now supplies a default source location when no explicit message is provided.

Example:

```text
Same assertion failed: slot-val.test.php:120
Expected: true
Actual:   false
```

Tests can still provide a semantic message:

```text
Same assertion failed: FormatterVal expected
Expected: true
Actual:   false
```

The fallback therefore answers:

> where did the assertion fail?

while an explicit test message answers:

> what invariant failed?

## Manual Renewal

Automatic certificate renewal is explicitly deferred.

Oderland cannot provide an API token scoped narrowly enough for safe unattended ACME/DNS renewal from Bredland.

Renewal therefore remains manual.

A likely operational workflow is:

1. run Certbot on Bredland;
2. maintain an authenticated SSH session to Oderland;
3. add the required `_acme-challenge` TXT record using available cPanel CLI tooling;
4. complete the ACME challenge;
5. remove the temporary TXT record;
6. install/reload the renewed certificate;
7. verify that the next Bredland heartbeat reports a healthy new `tls_cert_remaining`.

The exact renewal procedure is operational documentation rather than part of the monitoring architecture.

## Notes

The final telemetry contract is deliberately:

```text
tls_cert_remaining
```

rather than:

```text
tls_cert_expires_at
```

The original absolute-expiry design was useful during feasibility work but was not the final implementation.

The remaining-seconds representation allows the existing generic comparison machinery to express the Rule directly:

```text
tls_cert_remaining < 2592000
```

without adding injected-current-time or absolute-deadline compiler concepts.

Responsibility remains cleanly divided:

```text
Bredland
  ↓
reads installed certificate
  ↓
reports remaining seconds
  ↓
NOC Rule
  ↓
derives whether attention is required
  ↓
FormatterVal + display_duration
  ↓
persistent human-readable notification
```

Renewing the certificate changes the fact at the source.

No special notification lifecycle is necessary.

The compiler cleanup undertaken for BRD-034 was deliberately broader than the certificate feature itself because the required capability — rendering a formatted value inside notification text — exposed existing representation-specific magic.

Rather than implement "formatted notifications", the compiler was simplified so that **formatted values are ordinary values everywhere**.

That is the final architectural result of the slice.
